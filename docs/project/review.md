## Общая оценка

Начальная структура покрывает все 45 логических таблиц ТЗ и дополнена таблицами сессий и областей доступа. Выделены отдельные сущности коек, интервалов размещения, назначений врача и прикреплений пациента. Отсутствуют каскадные удаления медицинских событий. Ограничения исключения задают защиту от временных наложений на уровне БД.

Основные незакрытые вопросы касаются межтабличных правил и смысла исторических связей. Наличие внешнего ключа подтверждает существование записи, но не соответствие пациента, учреждения, специальности и даты. Блокировать дальнейшую подготовку документов не требуется; до демонстрации медицинских операций замечания приоритета P1 должны быть закрыты и проверены.

## Требования, которые нужно сделать однозначными

1. **Перевод пациента.** ТЗ требует перевод, но не уточняет перевод в другое отделение или другую больницу. Принятое решение модели: `hospitalizations.department_id` хранит отделение поступления, а фактическая история отделений определяется по койкам. Для одной госпитализации проверяется перевод между отделениями одной больницы; перевод в другую больницу требует отдельного сценария и не должен незаметно менять больницу прежней истории.
2. **Даты договоров.** `date` не задаёт часовой пояс преобразования `ordered_at`. При реализации следует явно определить дату договора по выбранному часовому поясу учреждения; тесты должны включать пограничные моменты суток.
3. **Стаж врача.** Требование упоминает дату расчёта, а пример сигнатуры — только идентификатор. В паспорте уже обоснован параметр `as_of_date`. Нужно определить единицу результата: полные годы либо дни с отдельным форматированием. Совместительство не увеличивает календарный стаж вдвое.
4. **Доступ после окончания лечения.** ТЗ говорит о разрешённых отношениях врача с пациентом, но не задаёт срок доступа после выписки. До утверждения правила нельзя автоматически разрешать бессрочный доступ всем когда-либо лечившим врачам.
5. **Статистика врача.** При нескольких местах работы и специальностях нужно определить зерно представления. Один приём нельзя засчитать несколько раз из-за JOIN с несколькими специальностями; операции с несколькими участниками также требуют явного смысла показателя.
6. **Отключённые койки.** Для процента занятости следует определить знаменатель: доступные к размещению койки или весь исторический инвентарь. Рекомендуется показывать активную вместимость отдельно от отключённого фонда и запрещать отключение занятой койки без перевода.
7. **Повторное направление.** `UNIQUE(referral_id)` не позволяет повторно применить направление даже после отмены госпитализации. Это допустимое правило, если отмена завершает направление; иначе требуется отдельное решение по жизненному циклу направления.

Эти уточнения не требуют останавливать проектирование: можно зафиксировать рабочую семантику и подтвердить её в окончательном ТЗ. До подтверждения они не выдаются за исходные требования преподавателя.

## Дополнительная проверка миграции 002

При чтении первой версии 002 выявлен обход в немедленном режиме ограничений: постановка проверки в очередь выполнялась до изменения данных. В текущем файле логика разделена: блокировка берётся `BEFORE STATEMENT`, а очередь создаётся `AFTER STATEMENT`. Это соответствует правилу видимости изменений: SQL в statement-level AFTER-триггере видит изменения вызвавшей команды. [Документация PostgreSQL о видимости изменений в триггерах](https://www.postgresql.org/docs/18/trigger-datachanges.html). Исправление требует отдельного регрессионного испытания IT-21; чтение файла не заменяет его выполнения.

Для действующего варианта с общей advisory-блокировкой есть обоснование свежести снимка: функции PL/pgSQL без явно заданной категории являются VOLATILE, и запросы внутри такой функции получают новый снимок на момент своего начала. Поэтому проверку после ожидания нельзя превращать в STABLE-функцию. Это вывод из правил PostgreSQL, а не доказательство конкретной конкурентной реализации. [Документация PostgreSQL о категориях изменчивости функций](https://www.postgresql.org/docs/18/xfunc-volatility.html).

Независимое доказательство для MEDCORE должно быть получено двумя серверными сессиями по IT-20. До этого конкурентная корректность считается непроверенной. Общая блокировка также сериализует изменения многих таблиц и глобальная проверка читает значительную часть базы; производительность и допустимая нагрузка пока не измерены. Будущая роль API не должна владеть таблицами или иметь возможность отключать триггеры и менять служебную очередь, что проверяется IT-19.

## Размещение в существующей схеме project

По явной инструкции пользователя таблицы приложения размещаются в `project`. На момент обследования схема на учебном PostgreSQL содержит `agencies`, `launch_sites`, `launches`, `orbit_dashboard` (представление), `orbital_data` и `space_objects`. Актуальная инструкция — сохранить старые объекты и перенести в отдельную схему `space_archive`. Ранее обсуждавшаяся очистка отменена и не описывается как выполненная. Перенос и установка MEDCORE не должны воздействовать на несвязанные объекты других схем.

Схему допустимо создавать через `CREATE SCHEMA IF NOT EXISTS project`, но совпадение имени таблицы, типа, функции или индекса приложения нельзя молча считать успешной миграцией. Для объектов MEDCORE необходима предварительная проверка коллизий и остановка при неожиданном существующем объекте. Архивирование старых объектов выполняется через транзакционный `ALTER ... SET SCHEMA`, а не удалением и повторным созданием. Целевая схема проверяется на коллизии таблиц, представления, связанных индексов и последовательностей. Динамические команды установки триггеров MEDCORE должны использовать явный список таблиц приложения.

До и после переноса фиксируются OID объектов, владельцы, права, контрольные количества строк, FK и зависимые объекты без паролей и токенов. Представление проверяется на выполнение после переноса. При неожиданном результате вся транзакция переноса должна откатиться. Отдельно проверяются внешние функции или запросы, содержащие текстовые ссылки на прежние имена: сохранение OID само по себе не гарантирует исправление произвольного SQL-текста. Изменение нескольких миграций MEDCORE проверяется поэтапно: отдельный COMMIT в каждой миграции означает, что сбой следующего файла не откатит предыдущий файл. План восстановления должен учитывать это без удаления архива. Преждевременное добавление таблицы учёта миграций не должно маскировать неполное применение.

Служебные GUC `medcore.actor_user_id`, `medcore.request_id` и имена PREPARE `medcore_q01`–`medcore_q12` не являются схемами и не требуют переименования. Замена должна касаться квалификаторов SQL, `search_path`, каталоговых проверок и тестов. Параметры подключения и локальный `.env` для этой проверки не читались.

Новые проверки приёмки IT-22–IT-24 описывают сохранный перенос старых объектов, коллизии и правильность пространства имён. Их наличие не означает выполненный перенос или применение миграций на сервере. Исполнение фикстур с ROLLBACK не является полностью немутирующей операцией: использованные значения последовательностей не возвращаются откатом строк.
