# Паспорт проекта и принятые решения

## Исходные сведения

Тема: «Разработка информационной системы для медицинских организаций города». Условное обозначение: MEDCORE. Разработчик: Яковлев Артём Сергеевич, группа 5996. Руководитель: Цымбалюк Лариса Николаевна. Срок сдачи: 11.05.2027. ФИО разработчика раскрыто по предоставленному прошлогоднему плану-графику; руководитель и срок подтверждены пользователем в чате.

Предметная область и учебные требования взяты из ТЗ версии 1.0 и пяти скриншотов задания. Три дополнительных скриншота задают визуальный ориентир. Шесть файлов прошлогоднего проекта используются как образцы; сведения о спортивном комплексе, Rust, MySQL, платёжных интеграциях и прежнем руководителе к MEDCORE не относятся.

## Приоритет источников

1. Прямые уточнения пользователя.
2. Выданная формулировка темы и требования преподавателя на скриншотах.
3. Предоставленное ТЗ MEDCORE, включая более подробные требования к реализации.
4. Применимые положения предоставленных стандартов для соответствующего вида документа.
5. Прошлогодний курсовой как пример структуры и оформления.

При содержательном противоречии фиксируется отдельное решение, а не молчаливое объединение несовместимых требований. Конкретное оформление основного альбома с рамками требует сверки с требованиями колледжа; поля старого файла сами по себе не доказывают нормативное требование.

## Архитектура

ADR-01. Используется трёхуровневая архитектура: React → ASP.NET Core API → PostgreSQL. Прямого доступа браузера к БД нет. Локальный запуск через Docker Compose должен быть воспроизводимым и не зависеть от облачных сервисов.

ADR-02. Сначала разрабатывается реляционная схема и её ограничения. SQL-миграции — источник структуры; EF Core применяется для операций с данными и не должен независимо изменять схему. Npgsql применяется для вызова процедур и специализированных запросов.

ADR-03. Для API выбрана ветка .NET 10 LTS: по [официальной политике Microsoft](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) срок поддержки охватывает сдачу проекта в мае 2027 года. Конкретный SDK и совместимые EF Core/Npgsql закрепляются перед реализацией. Учебный сервер проверен: PostgreSQL 18.0, расширения btree_gist и pg_trgm установлены. SQL используют range_agg и требуют не ниже PostgreSQL 14. Для первичного изолированного исполнения также используется PGlite. Три миграции и обе группы SQL-проверок успешно исполнены на учебном сервере; пользовательские проверки приложения ещё предстоят.

ADR-04. Ключи начальной схемы — bigint с GENERATED ALWAYS AS IDENTITY. Интервалы событий — timestamptz, полуоткрытые [начало, конец). Даты рождения и кадровые даты — date. Окончание NULL означает продолжающийся интервал. API будет передавать моменты времени с часовым поясом; интерфейс отображает их по выбранному часовому поясу.

ADR-05. Койка моделируется отдельной сущностью. Пересечение интервалов размещения ограничивается EXCLUDE USING gist. Аналогично запрещаются одновременные госпитализации одного пациента, несколько текущих лечащих врачей и пересекающиеся прикрепления к поликлинике. Проверка доступности в интерфейсе не заменяет ограничение БД.

ADR-06. Для исключения рассогласования начальная схема не хранит номер текущей койки и идентификатор текущего врача в госпитализации. Они выводятся из истории. Свободные места и показатели операций вычисляются, а не редактируются вручную.

ADR-07. Права состоят из роли и контекста. Врач получает доступ по подтверждённым отношениям с пациентом; администратор учреждения — в рамках своего учреждения; технический администратор не получает медицинские карты автоматически. В начальной схеме подготовлены таблицы пользователей, ролей и контекстных назначений. Политики доступа ещё предстоит реализовать и проверить.

ADR-08. Пользователи и медицинские записи деактивируются. Удаление пациента допустимо только для ошибочного черновика без медицинской истории. Каскадное удаление медицинских событий не используется. Запись автора отделяется от существования активной учётной записи.

ADR-09. Визуальный стиль — Glassy Dashboard V5: тёмная основа, стеклянные панели, мягкие блики и плавные переходы. Для таблиц и форм применяется более плотный фон. Будут поддержаны клавиатура и reduced motion. Три предоставленных референса определяют стиль, а не состав медицинских экранов.

ADR-10. По прямому уточнению пользователя все таблицы и остальные объекты БД MEDCORE размещаются в схеме `project`. Первоначальное имя схемы `medcore` заменено в SQL до серверного применения. Префиксы `medcore.actor_user_id`, `medcore.request_id` и имена prepared statements `medcore_q01`–`medcore_q12` — имена приложения, а не схемы. Старые таблицы космического проекта сохранены переносом в отдельную схему `space_archive`. Предшествовавшая просьба об удалении отменена; удаления не выполнялись.

## Уточнения ТЗ при проектировании

- В ТЗ функция стажа показана с одним параметром, но описана как расчёт на указанную дату. Планируемая сигнатура: `fn_doctor_experience(doctor_id, as_of_date DEFAULT CURRENT_DATE)`. Перекрывающиеся интервалы работы должны объединяться, чтобы совместительство не удваивало стаж.
- Для ролевой модели требуется контекст учреждения. Добавляется `user_organization_scopes` сверх предварительных 45 таблиц ТЗ.
- Для управляемых сессий добавляется `user_sessions`; хранится хеш секрета сессии, а не её открытый токен.
- Количество коек палаты в начальной схеме выводится из таблицы `beds`; домен положительной вместимости используется для плановой вместимости палаты. Соответствие фактического числа коек плану требует отдельной транзакционной проверки.
- Назначение лаборатории должно проверяться на дату заказа и по профилю исследования. Ссылка на договор сама по себе не подтверждает срок его действия.
- Статус `cancelled` предназначен для отменённой госпитализации. Такое событие не занимает койку; интервалы размещения создаются только при фактическом поступлении. Переходы статусов будут реализованы отдельно.

## Что ещё нельзя считать решённым

Номер варианта для обозначения документа, код МДК, требования к рамкам и точные реквизиты титульного листа текущего года пока не подтверждены. Номер 30 и старое обозначение документа не переносятся автоматически. Отзыв, подписи, допуск и согласование руководителя не создаются от его имени. Реальные медицинские данные в демонстрации не используются.
