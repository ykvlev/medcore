# План приёмочных проверок MEDCORE

Этот документ задаёт ожидаемое поведение для приёмки. Для сценариев по умолчанию установлен статус **«не выполнен»**; подтверждённые промежуточные факты отдельно указаны ниже и не означают, что вся приёмка завершена. Фактический результат, дата, версия приложения и доказательства заполняются после запуска. Подготовка сценария не считается успешным испытанием.

## Условия и тестовые данные

Испытания проводятся на отдельной учебной базе с вымышленными сведениями и воспроизводимым seed. До каждого независимого набора база возвращается в известное состояние. Проверяется версия миграций и параметры часового пояса. Пароли и действующие токены в протокол не включаются.

По уточнению пользователя все таблицы MEDCORE размещаются в схеме `project`. На момент обследования учебного сервера эта схема содержит старые объекты `agencies`, `launch_sites`, `launches`, `orbit_dashboard` (VIEW), `orbital_data`, `space_objects`. Актуальная инструкция пользователя — сохранить их и перенести в отдельную схему; ранее обсуждавшаяся очистка отменена. Для архива выбрано имя `space_archive`. Пять таблиц и представление перемещаются транзакционно через `ALTER ... SET SCHEMA`, с проверкой владельцев, зависимостей и количества строк. Другие схемы и несвязанные объекты не изменяются. Функциональные фикстуры с откатом предпочтительно выполнять в отдельной тестовой базе: ROLLBACK строк не восстанавливает потраченные значения последовательностей.

Параметры сеанса `medcore.actor_user_id` и `medcore.request_id`, а также имена подготовленных запросов `medcore_q01`–`medcore_q12` относятся к приложению, а не к схеме хранения. Они сохраняются. Ссылки на таблицы, типы и функции в SQL используют `project`.

## Подтверждённые промежуточные факты

По отчёту `docs/database/checks/space-archive-transfer.json` от 30.10.2026 транзакционный перенос `project` → `space_archive` выполнен: количества строк до/после совпадают для всех пяти таблиц. Для `agencies`, `launch_sites`, `launches` — по 0; для `orbital_data` — 68 762; для `space_objects` — 70 813. Представление после переноса проверено на выполнение; исходная схема не содержит перенесённых отношений. Отчёт не содержит отдельных доказательств совпадения всех OID/ACL, поэтому полный IT-22 по одному этому файлу не отмечается пройденным.

После замены пространства имён статически разобраны все шесть SQL-файлов: три миграции, два файла проверок и набор запросов. В квалификаторах объектов не осталось `medcore`; GUC аудита и 12 имён PREPARE сохранены. `tools/check-database.mjs` использует `project` для каталога и `search_path`.

Отчёт `docs/database/checks/educational-deployment.json` подтверждает применение трёх миграций на PostgreSQL 18.0: в `project` созданы 48 таблиц, 3 представления, 4 процедуры и 11 функций, включая служебные. Все три SHA-256 отчёта совпадают с текущими файлами миграций. Двенадцать подготовленных запросов скомпилированы на сервере; оба SQL-файла проверок выполнены успешно с откатом строк. Значения последовательностей могли увеличиться. Это фактические SQL-проверки, а не прохождение UI-сценариев или unit-тестов .NET. Проверки конкуренции двух сессий, прав API и пользовательских сценариев требуют отдельных результатов; обязательные TC и UT приложения пока не выполнены.

Базовый набор: больницы H1/H2, поликлиники P1/P2, два отделения D1/D2 больницы H1 и отделение D3 больницы H2; палаты с доступной, занятой и отключённой койками. Пациенты A/B имеют разные случаи. Врачи V1/V2 работают в H1, V3 — в H2, V4 имеет подходящее учёное звание для консультаций. Лаборатории L1/L2 имеют различающиеся профили и договоры. Для каждой из шести ролей создаются отдельные учётные записи и контексты.

Для конкурентных испытаний используются независимые подключения и транзакции. Два последовательно выполненных запроса не доказывают защиту от гонки.

## Пять обязательных функциональных тест-кейсов

### TC-01 Регистрация пациента

Предусловие: регистратор вошёл в систему и имеет доступ к P1. Тестовая запись отсутствует.

Шаги:

1. Открыть раздел пациентов и форму добавления.
2. Заполнить обязательные поля вымышленными значениями, выбрать разрешённую поликлинику.
3. Сохранить и открыть созданную карточку.
4. Проверить запись в PostgreSQL и аудит создания.

Ожидается: создан один пациент с идентификатором, введённые сведения совпадают с сохранёнными; при оформлении прикрепления создан один действующий интервал. Карточка отображается в списке. В аудит записаны действие, время, автор и идентификатор. Ошибка обязательного поля не оставляет частично созданной карточки.

Доказательство: скриншот формы/карточки, ответ API без секретов, контрольная выборка пациента и аудита.

### TC-02 Редактирование пациента

Предусловие: пациент A существует, регистратор имеет доступ. Известна текущая версия записи.

Шаги:

1. Изменить телефон и адрес через разрешённую форму.
2. Сохранить и заново открыть карточку.
3. Проверить БД и аудит.
4. Повторить попытку сохранения с устаревшей версией записи из второй сессии.

Ожидается: разрешённые поля обновлены, медицинские события сохранены; аудит перечисляет изменённые поля и автора. Вторая запись с устаревшей версией не затирает изменения молча: пользователь получает предусмотренный конфликт и может обновить форму. Точное отображение конфликта определяется контрактом API.

Доказательство: значения до/после, запись аудита, ответ на устаревшую версию.

### TC-03 Поиск пациента

Предусловие: набор содержит пациентов с совпадающими фрагментами ФИО и контрольные неподходящие записи, включая пациента с таким же ФИО и другой датой рождения.

Шаги:

1. Ввести фрагмент ФИО в другом регистре.
2. Установить доступные фильтры и перейти на следующую страницу.
3. Выполнить запрос, не имеющий совпадений.
4. Ввести строку с кавычкой и SQL-подобным текстом.

Ожидается: возвращаются только соответствующие доступные пользователю записи; порядок стабилен между страницами; общее количество согласовано с фильтром. Пустой поиск показывает понятное состояние. Специальная строка обрабатывается как данные, не меняет таблицы и не раскрывает диагностические сведения сервера.

Доказательство: параметры запроса и результаты для каждого набора, контрольная выборка из БД.

### TC-04 Госпитализация без свободных коек

Предусловие: пользователь имеет полномочия оформить госпитализацию; у пациента есть подходящее направление; все доступные койки выбранного отделения заняты. Известны количества событий до операции.

Шаги:

1. Попытаться оформить госпитализацию через интерфейс.
2. Повторить запрос непосредственно к API с идентификатором занятой койки.
3. Проверить госпитализации, размещения, назначения врача и статус направления.

Ожидается: сервер отклоняет операцию с понятным сообщением, не создаются частичные события; направление не помечается использованным только из-за неуспешной попытки. Занятость и медицинская история не изменены. Точный HTTP-код конфликта фиксируется в контракте API и соблюдается единообразно.

Доказательство: сообщение/ответ API, контрольные значения до/после и отсутствие незавершённых связей.

### TC-05 Запрет изменения диагноза регистратором

Предусловие: регистратор может просматривать разрешённую карточку пациента A; в ней есть диагноз. Записаны исходные значения и версия события.

Шаги:

1. Проверить доступные действия интерфейса.
2. Отправить прямой запрос на добавление, изменение и удаление диагноза.
3. Повторить для пациента B из чужого учреждения.
4. Проверить исходные диагнозы и аудит отказа.

Ожидается: команды медицинского редактирования не предлагаются; сервер самостоятельно отклоняет все запрещённые запросы. Для известного доступного объекта без полномочий ожидается 403; для чужого объекта допускается единая политика 403/404 без раскрытия его существования. Медицинские данные не меняются. Отказ фиксируется согласно политике аудита без записи лишних чувствительных данных.

Доказательство: ответы API, неизменность контрольных данных, события отказа.

| Код | Набор проверок | Входы и ожидаемое поведение |

| UT-01 `HospitalizationRulesTests` | Допустимость размещения | Свободная активная койка подходящего учреждения разрешена; занятая, отключённая или чужая койка запрещена. Интервалы [10:00,11:00) и [11:00,12:00) не пересекаются; [10:00,11:01) и [11:00,12:00) пересекаются. Конец до начала запрещён |

## Проверки прав шести ролей

Матрица задаёт минимальные проверки по ТЗ. «Разрешить» всегда означает в допустимом контексте организации, лаборатории или лечения. Дополнительная роль пользователя может расширять доступ только явным назначением. Полный доступ системному администратору к медицинским картам не подразумевается.

| Роль | Положительный сценарий | Обязательные отказы |
|---|---|---|
| Системный администратор | Создать пользователя, назначить роль, просмотреть разрешённый технический журнал | Открыть полную медицинскую карту только на основании технической роли; изменить диагноз без медицинских полномочий |
| Администратор организации | Изменить подразделение своего учреждения, получить его организационный отчёт | Изменить структуру H2 при контексте H1; назначить себе глобальную роль; получить полную медицинскую карту без отдельного основания |
| Врач | Создать медицинскую запись и диагноз у доступного пациента; просмотреть разрешённый результат | Изменить чужой случай без связи; изменить роли пользователей; получить чужой экспорт по идентификатору |
| Регистратор | Зарегистрировать пациента, изменить разрешённые контакты, записать на приём | Изменить диагноз, медицинскую запись или лабораторный результат; выполнить скрытую операцию прямым запросом |
| Сотрудник лаборатории | Получить назначенный своей лаборатории заказ и внести результат | Открыть заказ L2 при контексте L1; читать полную историю пациента; назначить себе права врача |
| Аналитик | Получить разрешённый агрегированный отчёт и его экспорт | Получить персональные карты, строки с избыточными идентификаторами или отчёт другого контекста; изменить исходные медицинские записи |

Для каждой роли проверяются список, одиночная запись, изменение, вложенные сущности и экспорт. Фильтрация списка сама по себе не защищает маршрут `/resource/{id}`. Дополнительно проверяются отсутствие сессии, истёкшая/отозванная сессия, деактивированный пользователь и изменение роли во время активной сессии.

## Проверка интерфейса и отчётов

Основные экраны работают с API, а не с фиксированными демонстрационными числами в коде. Создание события должно менять соответствующие показатели после обновления. Проверяются фильтр периода, стабильная пагинация, состояния загрузки/ошибки/пустого списка, управление клавиатурой и уменьшенная анимация. Таблицы и формы должны оставаться читаемыми на стеклянном фоне.

Для каждого из шести отчётов сверяются параметры, строки и итоги с независимым SQL. CSV открывается с корректной кодировкой и колонками, PDF читается без обрезки таблиц. Экспорт наследует полномочия пользователя, имеет управляемый срок доступности и не выдаётся другой сессии по подстановке идентификатора.

## Форма записи фактического результата

Для каждого выполненного сценария сохраняются: код; дата и исполнитель; версия кода/миграций; исходный seed; шаги и параметры; ожидаемый результат; фактический результат; статус «пройден/не пройден/заблокирован»; ссылка на доказательство; номер дефекта при наличии. После исправления фиксируется повторная проверка. Пропущенные сценарии не отмечаются пройденными.
