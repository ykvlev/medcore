# Методы защиты данных MEDCORE

Документ фиксирует фактическую основу раздела «Методы защиты данных» пояснительной записки. Он описывает только то, что реализовано в коде и проверено на учебной среде, и отдельно перечисляет ограничения и непроверенные места. Это не политика информационной безопасности организации и не заключение о соответствии законодательству: оценка по 152-ФЗ и отраслевым требованиям в рамках курсового проекта не проводилась.

## 1. Границы анализа и источники

Анализировались:

- серверная часть ASP.NET Core: [Program.cs](../../backend/Medcore.Api/Program.cs), [SessionAuthenticationHandler.cs](../../backend/Medcore.Api/SessionAuthenticationHandler.cs), [MedcoreStore.cs](../../backend/Medcore.Infrastructure/MedcoreStore.cs), [PatientStore.cs](../../backend/Medcore.Infrastructure/PatientStore.cs), [AdminStore.cs](../../backend/Medcore.Infrastructure/AdminStore.cs), [UserAccess.cs](../../backend/Medcore.Application/UserAccess.cs);

- фактические проверки: [api-report.json](../database/checks/api-report.json) (33 HTTP-проверки), [server-concurrency-report.json](../database/checks/server-concurrency-report.json) (12 утверждений о конкурентных транзакциях), [educational-deployment.json](../database/checks/educational-deployment.json) (развёртывание схемы), [backup-restore.json](../database/checks/backup-restore.json) (копирование и восстановление).

Система развёрнута на учебном PostgreSQL 18.0 в схеме `project`: 48 таблиц, 3 представления, 4 процедуры, 11 функций. Приложение работает с одной ролью БД, которая владеет схемой. Это ключевое ограничение: прикладные политики защищают API, но не разделяют доступ на уровне СУБД.

Данные в системе вымышленные. Тем не менее копии содержат персональные сведения учебных пациентов, хеши паролей и журнал аудита, поэтому к ним применяются те же требования обращения, что и к условно чувствительным данным.

## 3. Аутентификация

### 3.1 Хранение паролей

Пароли обрабатываются `PasswordHasher<UserEntity>` из ASP.NET Core Identity в режиме `IdentityV3` с `IterationCount = 210_000` ([MedcoreStore.cs](../../backend/Medcore.Infrastructure/MedcoreStore.cs), [AdminStore.cs](../../backend/Medcore.Infrastructure/AdminStore.cs)). Это PBKDF2 с HMAC-SHA512; в БД попадает только строка хеша, включающая соль и параметры. Открытый пароль не сохраняется и не возвращается API.

Свойства реализации:

- вход ищет пользователя по `lower(login)`; для этого есть уникальный индекс `uq_user_login` по `lower(login)`;
- при неверном логине всё равно выполняется проверка фиктивного хеша (`DummyHash`), чтобы снизить разницу во времени ответа;
- при `SuccessRehashNeeded` хеш пересчитывается с текущими параметрами;
- администратор задаёт пароль длиной от 8 до 128 символов; проверка сложности, истории и утечек не выполняется;
- смены собственного пароля и восстановления пароля через API нет: пароль задаёт `system_admin` при создании учётной записи;
- демонстрационные пользователи используют общий пароль из локального `LOCAL-ACCESS.md`; это допустимо только для учебного стенда.

### 3.2 Сессии и cookie

Сессия создаётся при успешном входе:

- 32 случайных байта из `RandomNumberGenerator` → 64 шестнадцатеричных символа; это 256 бит энтропии;
- в `project.user_sessions` хранится SHA-256 от токена (`token_hash`), а не сам токен; поле уникально;
- срок — 8 часов (`SessionHours = 8`), проверяется условием `expires_at > CURRENT_TIMESTAMP`;
- отзыв — `revoked_at`; выход выставляет его, отключение пользователя отзывает все его сессии;
- при каждом запросе `SessionAsync` дополнительно проверяет активность пользователя и сотрудника, затем заново загружает роли и области действия. Поэтому изменение ролей действует со следующего запроса, хотя сессия не отзывается.

Параметры cookie `medcore_session` ([Program.cs](../../backend/Medcore.Api/Program.cs)):

| Параметр | Значение | Комментарий |
|---|---|---|
| `HttpOnly` | `true` | JavaScript не читает токен |
| `SameSite` | `Lax` | cookie не отправляется с большинством межсайтовых POST |
| `Secure` | `Request.IsHttps` | на учебном HTTP-стенде `false` |
| `Path` | `/` | — |
| `MaxAge` | 8 часов | совпадает со сроком в БД |
| `IsEssential` | `true` | — |
| `Domain` | не задан | host-only cookie |

Сессии не привязаны к IP или user agent, не ротируются и не продлеваются: это фиксированное окно в 8 часов. Несколько параллельных сессий одного пользователя разрешены. Истечение срока и поведение при отзыве проверены не полностью: в [api-report.json](../database/checks/api-report.json) зафиксированы успешный вход, отказ анонимному запросу, отказ после выхода, но не проверено истечение 8 часов.

### 3.3 Вход, выход и ограничение попыток

- `POST /api/auth/login` — анонимный маршрут с политикой `login`.
- Ограничитель: `FixedWindowRateLimiter`, 20 запросов в минуту на `RemoteIpAddress`, очередь 0, `Retry-After: 60`, ответ 429 в формате Problem Details.
- Неверный логин или пароль → единый 401 «Неверный логин или пароль»; факт отказа пишется в `audit_logs` с `actor_user_id = NULL`.
- Успешный вход пишет `login/session/success` и создаёт сессию в одной транзакции.
- `POST /api/auth/logout` отзывает сессию по хешу токена и удаляет cookie; старый cookie после выхода отклоняется (проверено).
- Автоматической блокировки учётной записи после N неудач нет. Блокировка — это административное отключение `users.is_active`, которое отзывает все сессии. MFA, CAPTCHA и уведомления о входах отсутствуют.

### 3.4 CSRF, CORS и заголовки

Для небезопасных методов (POST, PUT, DELETE) до аутентификации выполняется проверка `Origin`: разрешены пустой `Origin`, текущий origin и в Development — `http://localhost:5173` / `http://127.0.0.1:5173`. CORS настроен на те же два локальных origin, методы GET/POST/PUT, `AllowCredentials`.

Дополнительно выставляются `X-Content-Type-Options: nosniff` и `Cache-Control: no-store`. Нет CSP, HSTS, `X-Frame-Options` и `Referrer-Policy`; HTTPS-редиректа нет, потому что учебный стенд работает по HTTP. Swagger UI и `/openapi/v1.json` доступны без аутентификации, `/health` — тоже.

Анти-CSRF-токена нет: защита строится на `SameSite=Lax` и проверке `Origin`. Пустой `Origin` разрешён намеренно для небраузерных клиентов, поэтому проверка не является универсальной.

## 4. Авторизация

### 4.1 Роли и области действия

Роли заданы справочником `project.roles` и ограничены шестью кодами CHECK-ограничением: `system_admin`, `organization_admin`, `doctor`, `registrar`, `lab_staff`, `analyst`. Связь пользователя с ролями — `user_roles`. Область действия роли — `user_organization_scopes`: учреждение либо лаборатория, ровно один объект (`num_nonnulls(...) = 1`), уникальность в рамках пользователя и роли.

`AccessAsync` при каждом запросе собирает роли, области учреждений и лабораторий, проверяет активность пользователя и связанного сотрудника. `system_admin` не имеет области действия; для `lab_staff` область — лаборатория; для остальных ролей — учреждение.

### 4.3 Контекст организации и лечения

Ключевой принцип: роль сама по себе не даёт доступа к медицинской карте. Для врача одновременно нужны область учреждения и подтверждённое лечебное отношение. В [MedcoreStore.cs](../../backend/Medcore.Infrastructure/MedcoreStore.cs) это выражено предикатом `CareCaseSql`: случай должен относиться к учреждению из области `doctor_orgs`, а врач должен встречаться хотя бы в одной из восьми связей — приём, диагноз, медицинская запись, назначение, направление, лабораторный заказ, участие в операции или история лечащего врача.

Регистратор видит пациента, если есть действующее прикрепление к поликлинике из его области (`patient_attachments` с интервалом, покрывающим текущий момент) либо открытый случай в учреждении из области. Изменение контактов дополнительно блокирует строку пациента `FOR UPDATE` и проверяет тот же предикат, поэтому нельзя обновить карточку вне области, даже зная идентификатор.

Для `system_admin` клинический обход намеренно отсутствует: политика `CanReadPatients` возвращает `false`, а `CanEditDiagnosis` — `false` даже при наличии отношения. Это проверено unit-тестом и HTTP-проверкой.

### 4.4 Проверка на сервере

Все проверки выполняются в API и хранилищах; скрытие кнопки в интерфейсе доказательством не считается. Ответы:

- 401 — нет или истекла сессия;
- 403 — роль или область не позволяют действие;
- 404 — объект не найден в доступной области (чтобы не раскрывать существование чужого объекта);
- 409 — конфликт версии или ограничение данных;
- 429 — превышение лимита входа.

Фактические подтверждения: 33 HTTP-проверки в [api-report.json](../database/checks/api-report.json), включая шесть ролей, запрет пациентов для `system_admin`, запрет диагноза регистратору (403), отказ врачу без лечебного отношения, отказ после выхода; 12 утверждений о конкурентных транзакциях в [server-concurrency-report.json](../database/checks/server-concurrency-report.json). Это выборочные сценарии, а не полная матрица всех ролей и объектов.

### 4.5 Ограничения авторизации

- Одна роль БД владеет схемой и используется приложением. Разделения прав на уровне PostgreSQL нет: роль API не ограничена отдельными таблицами, а владелец может обойти `REVOKE ... FROM PUBLIC`.
- Справочник учреждений доступен для чтения всем аутентифицированным ролям; это не медицинские данные, но и не минимально необходимое.
- Экспорт отчёта не проверяет отдельное право на экспорт: он использует ту же проверку `ReportAsync`, что и просмотр, и не пишется в `audit_logs` и `report_exports`.
- Изменения сотрудников не аудируются (в `EmployeeStore` нет вызовов аудита).
- Отказы 403 не аудируются; в журнал попадают входы, выходы, чтение карточки пациента, изменения пациентов, диагнозы, госпитализации, лабораторные заказы/результаты, учреждения/корпуса/отделения/палаты/койки и административные изменения.
- Полнота проверки прав на все маршруты не доказана: часть сценариев стационара и лаборатории в HTTP-отчёте не покрыта.

## 5. Защита запросов и SQL

### 5.1 Параметризация

Основной слой доступа — EF Core/Npgsql. Значения передаются через `NpgsqlParameter`/`AddWithValue` с явным `NpgsqlDbType`; в SQL-тексте остаются только имена параметров (`@id`, `@orgs`, `@search`). Это относится к чтению пациентов, госпитализациям, лабораториям, отчётам и административным операциям.

Сырой SQL применяется там, где нужны представления, процедуры и сложные предикаты:

- `db.Patients.FromSqlRaw(PatientAccessQuery, parameters)` — предикат собран из констант, значения переданы параметрами;
- `SELECT ... WHERE ... ({CareCaseSql})` — интерполируется только константный текст, не пользовательские данные;
- вызовы `CALL project.sp_*` — аргументы параметризованы.

В коде есть строковая интерполяция SQL, но в неё попадают только константные фрагменты (`PatientAccessSql`, `CareCaseSql`, `RegistrarPatientSql`, `HospitalReadPredicate`). Это безопасно при текущем коде, но хрупко: если при будущей правке в интерполяцию попадёт значение из запроса, появится инъекция. Правило для сопровождения: пользовательские значения — только через параметры.

### 5.2 Контекст аудита через GUC

Перед изменением пациента приложение выполняет в транзакции:

```sql
SELECT set_config('medcore.actor_user_id', @actor, true),
       set_config('medcore.request_id', @request, true)
```

Третий аргумент `true` делает настройку локальной для транзакции. Триггер `fn_audit_patient_changes` читает `medcore.actor_user_id`, проверяет, что это существующий активный пользователь, и пишет автора, изменённые поля и `request_id` в `audit_logs`. `request_id` — `HttpContext.TraceIdentifier`, сгенерированный сервером, а не произвольный заголовок клиента.

GUC — кооперативный механизм: он не защищает от прямого SQL-доступа. Лицо, подключённое к БД, может выставить `medcore.actor_user_id` другого активного пользователя и тем самым исказить атрибуцию. Это ограничение модели доверия, а не ошибка API.

### 5.3 Валидация входа

- DataAnnotations на контрактах: обязательность, длины (логин 128, пароль 1024, ФИО 100, телефон 50, email 254, адрес 500, примечание 2000), `EmailAddress`, `RegularExpression` для пола, `Range` для идентификаторов и версии.
- Ручные проверки: дата рождения не в будущем, поликлиника существует и активна, страница ≥ 1, размер страницы 1–100, длина поиска ≤ 100, период отчёта, статусы госпитализации, роли и области действия.
- Поиск использует `ILIKE` с параметром `%...%`; символы `%` и `_` не экранируются. Это меняет семантику поиска (шаблон), но не является SQL-инъекцией. Очень широкая маска может быть дорогой; индексы `pg_trgm` снижают риск.
- Ограничения БД (CHECK, FK, EXCLUDE, уникальные индексы) остаются последней линией защиты; API не пытается заменить их проверками на клиенте.

Отдельные тесты с payload вида `' OR 1=1 --` не зафиксированы. Утверждение «инъекция невозможна» основано на анализе кода (параметризация), а не на выполненном наборе атакующих строк.

### 5.4 Привилегии БД и search_path

- Подключение: `SearchPath = "project,public"`, `IncludeErrorDetail = false`, таймауты 10/30 с.
- Хранимые функции имеют `SECURITY INVOKER` и фиксированный `search_path = pg_catalog, project`, что снижает риск подмены объектов через схему.
- Для процедур и внутренних функций выполнено `REVOKE ALL ... FROM PUBLIC`; это защищает от вызова через `PUBLIC`, но не от владельца схемы.
- Роль учебного сервера не суперпользователь и не может создавать роли (`rolcreaterole = false`), поэтому отдельная минимально привилегированная роль API не создана. Это главный нерешённый вопрос защиты на уровне СУБД.
- Приложение подключается той же ролью, которая владеет схемой. Следствие: при компрометации процесса API или `.env` доступны все таблицы, включая аудит и хеши паролей.

### 5.5 Ошибки и заголовки

`UseExceptionHandler` преобразует исключения в Problem Details: `ApplicationFault` сохраняет свой статус и бизнес-сообщение; `PostgresException` маппится по SQLSTATE (400, 404, 409, 503); для 5xx клиент получает общее сообщение и `traceId`. Текст SQL, имена ограничений и стек не возвращаются. Для 5xx в лог пишется только тип исключения, что снижает утечку, но затрудняет диагностику.

## 6. Аудит

### 6.1 Модель

`project.audit_logs` содержит: `id`, `actor_user_id`, `occurred_at`, `action`, `entity_type`, `entity_id`, `changed_fields text[]`, `request_id`, `outcome` (`success`/`failure`/`denied`). Индексы: по автору и времени, по объекту и времени.

Просмотр журнала — только `system_admin` через `GET /api/admin/audit` с фильтрами периода и действия. Dashboard показывает пользователю его собственные последние события; `system_admin` дополнительно видит события типов `session`, `user`, `role`.

### 6.2 Что фиксируется

| Событие | Action / entity | Где реализовано |
|---|---|---|
| Успешный вход | `login` / `session` | `MedcoreStore.LoginAsync` |
| Неудачный вход | `login` / `session`, outcome `failure`, автор NULL | `MedcoreStore.LoginAsync` |
| Выход | `logout` / `session` | `MedcoreStore.LogoutAsync` |
| Чтение карточки пациента | `read` / `patient` | `PatientStore.PatientAsync` |
| Создание, изменение, удаление пациента | `insert`/`update`/`delete` / `patient`, изменённые поля | триггер `fn_audit_patient_changes` |
| Диагноз | `insert` / `case_diagnosis` | `PatientStore.AddDiagnosisAsync` |
| Поступление, перевод, смена врача, выписка, направление | соответствующие action / `hospitalization`, `referral` | `HospitalizationStore` |
| Лабораторный заказ и результат | `insert` / `lab_order`, `lab_result` | `LaboratoryStore` |
| Учреждение, корпус, отделение, палата, койка | `insert`/`update` / соответствующий тип | `OrganizationStore` |
| Учётная запись, роли | `insert`/`update`/`role_change` / `user` | `AdminStore` |

### 6.3 Ограничения аудита

- Журнал хранится в той же БД и той же схемой, что и защищаемые данные. Владелец схемы может изменить или удалить записи; append-only триггера, запрета UPDATE/DELETE, хеш-цепочки и внешней копии нет.
- Нет IP-адреса, user agent и результата авторизации; отказы 403 не пишутся.
- Изменения сотрудников (`EmployeeStore`) не аудируются.
- Экспорт отчётов не аудируется и не создаёт запись в `report_exports`; таблица `report_exports` пока не используется.
- Нет регламента хранения, архивирования и очистки; журнал растёт вместе с демонстрационной нагрузкой (на момент проверки — более тысячи записей).
- Атрибуция через GUC кооперативная (см. 5.2).

## 7. Резервное копирование и восстановление

### 7.1 Реализация

- [backup-db.mjs](../../tools/backup-db.mjs) — копия схемы `project` в пользовательском формате `pg_dump` (`custom`), с расширениями `btree_gist` и `pg_trgm`; `space_archive` — только по флагу `--include-archive`.
- [restore-db.mjs](../../tools/restore-db.mjs) — восстановление только в явно указанную БД `--database=...`; отказ, если имя совпадает с рабочей БД из `.env`, если это служебная БД, если в цели уже есть схемы `project`/`space_archive`, если SHA-256 не совпадает.
- Оба скрипта читают `.env`, требуют `PGPASSWORD` из окружения, не запрашивают пароль интерактивно и не печатают его. `pg_dump`/`pg_restore` ищутся в `PATH` и стандартных каталогах; путь можно задать через `PG_DUMP`/`PG_RESTORE`.
- Имя файла содержит UTC-метку: `medcore_project_only_<метка>_<YYYYMMDDTHHMMSSZ>.dump`; рядом — `.manifest.json`.

### 7.2 Манифест и целостность

Манифест содержит: версию формата, время, путь, размер, SHA-256, формат, БД и пользователя, схемы, версию PostgreSQL и `pg_dump`, путь и признак `pgDumpOnPath`, расширения, количество таблиц/представлений/процедур/функций, количество строк в 10 ключевых таблицах, длительность, число предупреждений и команду восстановления. Пароль в манифест не попадает.

Restore повторно считает SHA-256 и размер, сверяет с манифестом и читает оглавление архива через `pg_restore --list` до записи в БД. Восстановление выполняется с `--no-owner --no-privileges --single-transaction --exit-on-error`: при ошибке не остаётся частично восстановленной схемы, а владельцы и ACL не переносятся (роль не может создавать роли).

### 7.3 Проверка после восстановления

Скрипт сверяет:

- количество строк в 10 ключевых таблицах: `medical_organizations`, `departments`, `beds`, `employees`, `doctors`, `patients`, `medical_cases`, `appointments`, `hospitalizations`, `bed_occupancies`;
- наличие трёх представлений: `vw_hospital_capacity`, `vw_doctor_statistics`, `vw_patient_treatment_summary`;
- наличие четырёх процедур: `sp_register_patient`, `sp_update_patient`, `sp_delete_patient_draft`, `sp_get_patient_summary`;
- общее количество объектов: 48 таблиц, 3 представления, 4 процедуры, 11 функций;
- установку расширений `btree_gist` и `pg_trgm`;
- код возврата `pg_restore` и отсутствие ошибок применения.

### 7.5 Ограничения резервного копирования

- Копия не шифруется; SHA-256 подтверждает целостность, но не конфиденциальность.
- Нет автоматического расписания, хранения вне машины, ротации и проверки на другом хосте.
- Нет WAL-архивирования и восстановления на момент времени (PITR); копия логическая, на момент запуска.
- Проверка восстановления выполнена на локальном кластере, а не на учебном сервере; это подтверждает переносимость копии и работу скриптов, но не снимает ограничение среды.
- Сверяются 10 ключевых таблиц и наличие объектов, а не полное построчное равенство всех 48 таблиц.

## 8. Ограничения среды

1. **Нет TLS до PostgreSQL.** Учебный сервер не поддерживает SSL; `PGSSLMODE=disable`, `pg_stat_ssl.ssl = false`. Пароль и данные передаются по сети в открытом виде. Это зафиксировано в [database/README.md](../../database/README.md).
2. **Нет права CREATE ROLE.** Роль не суперпользователь и не может создавать роли, поэтому минимально привилегированная роль API не создана. `REVOKE ... FROM PUBLIC` полезен, но владелец схемы сохраняет полный доступ.
3. **Нет права CREATE DATABASE.** Подтверждено фактической попыткой: SQLSTATE 42501. Поэтому восстановление на учебном сервере не выполнено; для него нужен администратор СУБД.
4. **Одна учебная БД и общий сервер.** В кластере видны базы других студентов; доступ к чужим базам запрещён правами. Работать разрешено только в своей БД и схеме `project`.
5. **HTTP-стенд.** Приложение и фронтенд работают по HTTP на localhost; cookie `Secure` не выставляется, HSTS и HTTPS-редирект отсутствуют.
6. **Секреты в локальных файлах.** `.env` и `LOCAL-ACCESS.md` исключены из Git, но хранятся на рабочей машине; хранилища секретов нет. Демонстрационный пароль общий для шести учётных записей.
7. **Ограниченная доказательная база.** SQL-проверки в PGlite не являются проверкой реального многопользовательского сервера; HTTP-проверки не заменяют браузерные тесты; конкурентные проверки покрывают отдельные сценарии.
8. **Нет платформенных средств защиты.** Нет WAF, IDS, централизованного логирования, резервного питания и мониторинга; это учебный локальный стенд.

## 9. Что не проверено

Ниже перечислено, что не проверено в рамках этой работы. Отдельные сценарии могли выполняться другими задачами проекта; здесь они не подтверждаются.

| Область | Статус | Причина |
|---|---|---|
| Восстановление на учебном сервере | не выполнено | нет права `CREATE DATABASE`; отказ 42501 зафиксирован |
| Истечение сессии через 8 часов | не проверено | нет автоматического теста; проверялись вход/выход/отказ |
| Блокировка после серии неудачных входов | не реализовано | есть только лимит 20/мин на IP |
| CSRF в реальном браузере | не проверено | нужен браузерный сценарий с межсайтовой формой |
| XSS и CSP | не проверено | CSP не настроен; тесты не проводились |
| SQL-инъекции payload-строками | не проверено | защита следует из параметризации, тест не зафиксирован |
| Полная матрица ролей и объектов | частично | 33 HTTP-проверки покрывают основные роли, не все маршруты |

| Разделение прав на уровне PostgreSQL | не реализовано | роль не может создавать роли |
| Нагрузочное и DoS-тестирование | не проводилось | нет стенда и методики |
| Сканирование зависимостей и статический анализ | не проводилось | вне объёма этапа |
| Соответствие 152-ФЗ и отраслевым нормам | не проводилась | требуется юридическая оценка, не технический вывод |

## 10. Приоритетные меры

**Первоочередные (до эксплуатации с реальными данными):**

1. Создать отдельную роль PostgreSQL с минимальными правами (SELECT/INSERT/UPDATE на необходимые объекты, EXECUTE на согласованные процедуры) и подключать API только под ней; владелец схемы не должен использоваться приложением.
2. Включить TLS для PostgreSQL и HTTPS для приложения; выставить `Secure`, HSTS, CSP и `X-Frame-Options`.
3. Шифровать резервные копии, хранить их вне машины с ограниченным доступом, добавить расписание и регулярную проверку восстановления.
4. Сделать аудит append-only: запрет UPDATE/DELETE для прикладной роли, отдельная схема/БД или внешнее хранилище, хеш-цепочка.
5. Ограничить доступ к `.env` и `LOCAL-ACCESS.md`, сменить демонстрационный пароль, ввести индивидуальные пароли.

**Следующие:**

6. Политика паролей (сложность, срок, история), смена/сброс пароля, MFA для `system_admin`.
7. Блокировка учётной записи после серии неудач и уведомления о входах.
8. Анти-CSRF-токен в дополнение к `SameSite`/`Origin`; глобальный rate limit для дорогих отчётов и экспорта.
9. Аудит отказов 403, изменений сотрудников, экспорта отчётов; IP/user agent.
10. Расширить отрицательные тесты API на все роли и маршруты; добавить payload-тесты поиска; браузерные тесты CSRF/XSS.
11. Ротация сессий, ограничение числа параллельных сессий, привязка к устройству (по необходимости).
12. Регулярное сканирование зависимостей, статический анализ, пентест; оценка соответствия 152-ФЗ.

## 12. Вывод

В MEDCORE реализован рабочий базовый контур защиты: пароли хранятся только в виде медленного хеша, сессии управляются на сервере и отзываются, прикладные роли ограничены организацией и лечебным отношением, SQL параметризован, действия и входы попадают в аудит, резервная копия создаётся и проверяется восстановлением в отдельную БД. Эти меры подтверждены фактическими проверками, а не только описанием схемы.

При этом система не готова к обработке реальных медицинских данных без дополнительных мер: нет TLS, разделения прав на уровне СУБД, шифрования и внешнего хранения копий, неизменяемого аудита и полноценной политики паролей. Ограничения учебной среды (отсутствие SSL, `CREATE ROLE`, `CREATE DATABASE`) зафиксированы честно; часть проверок остаётся невыполненной и перечислена в разделе 9.
