# ВВЕДЕНИЕ

Медицинские организации города работают со взаимосвязанными сведениями об учреждениях, персонале, пациентах и лечебных мероприятиях. Прикрепление пациента к поликлинике, направление на стационарное лечение, размещение в палате и выполнение лабораторного исследования образуют последовательность событий. Для их согласованного учёта необходимо сохранять связи между записями и историю изменений, а также разграничивать полномочия сотрудников.

Актуальность темы курсового проекта определяется необходимостью обеспечить целостность данных при совместной работе нескольких медицинских организаций. Ошибочное размещение двух пациентов на одной койке, потеря истории при изменении прикрепления и выполнение исследования без действующего договора являются примерами ситуаций, которые должна предотвращать информационная система. Решение этих задач требует применения не только пользовательских форм, но и ограничений реляционной базы данных, транзакций и серверных проверок доступа.

Объект исследования — процессы информационного взаимодействия медицинских организаций города при учёте персонала, пациентов и оказанной помощи; предмет — методы проектирования, разработки и защиты реляционной базы данных, обеспечивающей эти процессы.

Цель курсового проекта — разработать информационную систему MEDCORE для медицинских организаций города с централизованной базой данных PostgreSQL, веб-интерфейсом и разграничением доступа к сведениям в соответствии с полномочиями пользователей.

Для достижения поставленной цели необходимо решить следующие задачи:

1. Проанализировать предметную область и определить требования к системе.

2. Построить функциональную и информационную модели, выделить сущности, атрибуты и связи.

3. Разработать нормализованную реляционную схему и определить ограничения целостности.

4. Создать таблицы, индексы, представления, процедуры, функции и триггеры PostgreSQL.

5. Реализовать серверное приложение на C# с использованием ASP.NET Core и клиентское приложение на React с TypeScript.

6. Обеспечить регистрацию и поиск пациентов, учёт сотрудников, госпитализаций и лабораторных исследований, формирование отчётов.

7. Реализовать аутентификацию, авторизацию и аудит операций, а также спроектировать сценарий резервного копирования с проверкой восстановления.

8. Выполнить функциональное и автоматизированное тестирование, подготовить пользовательскую и техническую документацию.

В работе использованы методы анализа предметной области, функционального моделирования, проектирования и нормализации реляционных баз данных, а также модульного и интеграционного тестирования; реализация построена по трёхуровневой архитектуре.

Практическая значимость проекта — учебный программный продукт, демонстрирующий согласованную обработку медицинских событий, применение хранимых объектов PostgreSQL и проверку прав доступа. Демонстрация использует вымышленные данные, а сведения о проверках приводятся только по сохранённым машинным протоколам.

# 1 ПОСТАНОВКА ЗАДАЧИ И АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ

## 1.1 Характеристика предметной области

Объектом автоматизации является информационное взаимодействие больниц, поликлиник и лабораторий города. Больница включает один или несколько корпусов, в которых располагаются отделения. Каждое отделение имеет специализацию и палаты с отдельными койками. Поликлиника может быть административно закреплена за больницей либо работать самостоятельно. Лаборатория оказывает услуги нескольким учреждениям при наличии договоров и необходимых исследовательских профилей.

Персонал учреждений включает врачей и сотрудников других категорий; для врача учитываются специальности, научная степень, учёное звание и интервалы трудоустройства, причём одновременно допускается работа не более чем в одной больнице и одной поликлинике. Пациент прикрепляется к поликлинике на определённый период, а при стационарном лечении в каждый момент времени имеет одного лечащего врача; смена прикрепления, врача и койки сохраняется как самостоятельные интервалы истории.

## 1.2 Объекты автоматизации и основные процессы

Функциональная модель построена по методологии IDEF0. Контекстная диаграмма A-0 (рисунок А.1) представляет систему как единую функцию «Управлять медицинской информацией организаций города». Входами являются сведения об учреждениях, персонале, пациентах и медицинских событиях; выходами — согласованные справочники, медицинская история и отчётность; управлением — требования ТЗ, правила предметной области и ограничения доступа; механизмами — сервер приложения, СУБД PostgreSQL и клиентское приложение. Декомпозиция контекстной функции (рисунок А.2) выделяет шесть процессов: управление организациями и структурой, учёт персонала, регистрацию пациентов, амбулаторное лечение, стационарное лечение и лабораторные исследования. Декомпозиция отражает фактическое разделение модулей базы данных и приложения, поэтому используется как основа дальнейшего изложения. Процесс управления организациями включает регистрацию учреждения и настройку его структуры. Входными данными являются сведения об учреждении, корпусах, отделениях и палатах. Результатом служит согласованный справочник структуры, применяемый при трудоустройстве персонала и размещении пациентов.

Процесс учёта персонала включает создание карточки сотрудника, назначение специальностей и регистрацию трудовых отношений. При сохранении проверяются допустимость совместительства и соответствие научной степени учёному званию. Показатели операций рассчитываются по медицинским событиям, поэтому не требуют отдельного ручного ввода в карточке врача.

Процесс регистрации пациента включает ввод идентифицирующих и контактных сведений, проверку обязательных полей и оформление прикрепления к поликлинике. Поиск по ФИО помогает находить ранее зарегистрированных пациентов. Совпадение ФИО и даты рождения требует проверки, но само по себе не доказывает, что записи принадлежат одному человеку.

Процесс амбулаторного лечения начинается с медицинского обращения. В рамках случая назначаются приёмы, фиксируются диагнозы и медицинские записи. При необходимости оформляются направления на госпитализацию и исследования. Регистратор управляет организационными сведениями, а медицинские записи создаёт пользователь с соответствующими полномочиями.

Процесс госпитализации включает выбор учреждения, отделения и доступной койки, назначение лечащего врача и фиксацию поступления. Проверка свободного места и создание размещения выполняются в одной транзакции. При переводе закрывается прежний интервал размещения и открывается новый. Выписка завершает госпитализацию, размещение и текущее назначение врача согласованно.

Процесс лабораторного исследования включает создание заказа, проверку договора с направляющим учреждением, соответствия профиля и регистрацию результата. Результат связан с исходным заказом, что позволяет определить пациента и лабораторию без повторного ввода этих сведений. Отчётность строится на агрегированных сведениях о коечном фонде, пациентах, госпитализациях, нагрузке врачей, операциях и исследованиях; период и область доступных учреждений задаются явно, а экспорт не расширяет права пользователя по сравнению с просмотром.

## 1.3 Пользователи и разграничение полномочий

Система рассчитана на одиннадцать ролей. Шесть ролей определены исходными требованиями, пять добавлены при развитии проекта: главный врач, заместитель главного врача, заведующий отделением, министр здравоохранения и губернатор. Ролевой принадлежности недостаточно для определения доступа к каждой записи: сервер дополнительно учитывает область действия — учреждение, отделение, лабораторию, город или регион — и наличие допустимого отношения между врачом и пациентом. Скрытие команды в интерфейсе используется для удобства, но решение о доступе принимается сервером. Состав ролей и их полномочий приведён в таблице 1; диаграмма вариантов использования приведена в приложении А (рисунок А.3).

## 1.7 Обзор существующих подходов и аналогов

Прямое сравнение с промышленными МИС ограничено: их модели данных и правила доступа не публикуются в объёме, достаточном для проверяемого сопоставления. Обзор построен на трёх классах решений, характеристики которых подтверждаются открытыми источниками.

Первый класс — комплексные МИС, охватывающие регистратуру, стационар, лабораторию и отчётность в едином контуре. Их преимущество — готовые рабочие места и регламенты, ограничение для учебного проекта — закрытость схемы данных.

Второй класс — универсальные платформы с настраиваемыми справочниками: объекты описываются быстро, но правила чаще реализуются кодом приложения, а не ограничениями СУБД, что требует дополнительных транзакционных проверок.

Третий класс — стандартизованный обмен данными: спецификация HL7 FHIR Release 4 определяет ресурсы `Patient`, `Practitioner`, `Organization`, `Encounter`, `Observation` и правила их поиска [14]. ## 2.1 Подход к проектированию и состав модели

Проектирование выполнялось в последовательности «предметные правила → логическая модель → реляционная схема → ограничения СУБД». Источником структуры являются SQL-миграции: объектно-реляционный отображатель EF Core применяется только для операций с данными и не изменяет схему независимо. Такое решение исключает ситуацию, когда два инструмента по-разному описывают одни и те же ограничения.

Модель включает 48 отношений: 47 таблиц создаются в первой миграции, 48-я — служебная очередь проверок целостности во второй миграции. Из 47 таблиц первой миграции 45 описывают предметную область, две (`user_organization_scopes`, `user_sessions`) добавлены для управления доступом и сессиями. Наличие таблицы не означает готовность пользовательского сценария; фактическое использование объектов приложением описано в разделе 4.

Распределение таблиц по функциональным группам совпадает с листами физической схемы (приложение А) и с модулями приложения: организации и структура — 8 таблиц (`medical_organizations`, `hospitals`, `polyclinics`, `buildings`, `department_specializations`, `departments`, `wards`, `beds`); персонал — 10 таблиц (`employee_categories`…`specialty_conditions`); пациенты и случаи — 6 таблиц; лечение и стационар — 9 таблиц; лаборатории — 7 таблиц; доступ, аудит и отчётность — 7 таблиц; служебная очередь `business_rule_checks` — 1 таблица. ## 2.4 Функциональная и информационная модели

Функциональная модель (рисунки 1 и 2) определяет состав процессов, информационная модель — состав данных для их выполнения; переход выполнен по схеме «событие процесса → сущность события → атрибуты и связи». Например, госпитализация порождает сущность `hospitalizations` и два интервальных отношения — `bed_occupancies` и `attending_physician_history`. Информационная модель строится на трёх принципах: событие хранится один раз, справочные и событийные данные разделены, время выражается явно — у каждого события есть начало, а у продолжающегося события конец интервала не заполнен.

Принятая семантика интервалов — полуоткрытая: интервал `[начало, конец)` включает начало и исключает конец. Поэтому размещение, завершённое в 10:00, и следующее размещение, начатое в 10:00, не пересекаются, а перевод пациента в момент времени T не создаёт ни наложения, ни разрыва. Такая семантика соответствует документации PostgreSQL по диапазонным типам [9] и позволяет выразить требование «не более одного» ограничением `EXCLUDE`, не прибегая к триггерам на каждую вставку.

Из ER-модели в реляционную перенесены не все логические связи: связь «пациент — койка» восстанавливается через госпитализацию и интервал размещения, а связь «врач — пациент» выводится из участия врача в событиях случая. Это устраняет рассогласование между явно сохранённой связью и фактическими событиями.

Модуль «Пациенты и случаи» (рисунок А.9) и модуль «Стационар» (рисунок А.10) показывают отношения, в которых сосредоточены основные правила целостности. В модуле стационара видно разделение трёх временных рядов: госпитализация задаёт общий интервал, размещения задают место, назначения задают лечащего врача.

## 2.5 Реляционная модель и ключи

Реляционная модель использует суррогатные первичные ключи `bigint`, порождаемые `GENERATED ALWAYS AS IDENTITY`. Суррогатный ключ не зависит от предметных значений, устойчив при исправлении ошибочного номера и уменьшает размер внешних ключей по сравнению с составными естественными ключами. Естественные уникальности при этом сохранены: номер корпуса уникален в пределах больницы, номер палаты — в пределах отделения, номер койки — в пределах палаты, код специальности и код диагноза уникальны глобально.

Для связей «многие ко многим» применяются составные первичные ключи: (`doctor_id`, `specialty_id`) в `doctor_specialties`, (`appointment_id`, `doctor_id`) в `appointment_doctors`, (`surgery_id`, `doctor_id`) в `surgery_participants`, (`user_id`, `role_id`) в `user_roles`, (`laboratory_id`, `profile_id`) в `laboratory_profile_links`. Составной ключ одновременно запрещает повторное назначение и обеспечивает индекс для обратного поиска.

Ряд отношений имеет несколько кандидатных ключей. В `medical_cases` ключами являются `id` и пара (`id`, `patient_id`); вторая уникальность введена для составного внешнего ключа из `hospitalizations`. В `case_diagnoses` кандидатным ключом является `id`, а частичный уникальный индекс `uq_case_primary_diagnosis` ограничивает одним основным диагнозом на случай. В `surgery_participants` частичный индекс `uq_surgery_lead` допускает только одного ведущего врача на операцию.

## 2.6 Нормализация и функциональные зависимости

Нормализация проверялась по функциональным зависимостям, а не по количеству таблиц. Первая нормальная форма обеспечена атомарностью столбцов: списки вынесены в связующие таблицы, составные значения не хранятся в текстовых полях. Исключение — два служебных столбца (`audit_logs.changed_fields`, `report_exports.parameters`), которые не участвуют в предметных связях.

Вторая нормальная форма проверена для отношений с составными ключами. В `doctor_specialties` атрибуты `certified_on` и `valid_until` зависят от полной пары (`doctor_id`, `specialty_id`) и описывают именно факт наличия специальности у врача. В `surgery_participants` атрибуты `specialty_id` и `participation_role` зависят от пары «операция — врач», а не от одного из ключей. Аналогично устроены `appointment_doctors`, `user_roles` и `laboratory_profile_links`.

Третья нормальная форма проверена по транзитивным зависимостям. В `wards` атрибут `planned_capacity` зависит от ключа палаты, а не от отделения; вместимость отделения не хранится и вычисляется агрегированием. В `lab_orders` пациент и лаборатория не хранятся, поскольку выводятся через случай и договор. В `attending_physician_history` специализация врача не дублируется: она берётся из `doctor_specialties` в момент проверки.

Два дублирования приняты осознанно. Первое — `hospitalizations.patient_id` при наличии `case_id`: пациент уже определён случаем, поэтому формально это транзитивная зависимость. Дублирование необходимо, чтобы ограничение `EXCLUDE` по пациенту и составной внешний ключ (`case_id`, `patient_id`) работали без триггеров: первый запрещает два одновременных стационара одного пациента, второй не позволяет связать госпитализацию с чужим случаем. Второе — дискриминатор `organization_type` в подтипах: он повторяет тип из `medical_organizations`, но именно составной внешний ключ по паре (`id`, `organization_type`) делает невозможным существование поликлиники с типом больницы.

Четвёртая нормальная форма обеспечена устранением многозначных зависимостей: специальности врача, профили лаборатории и участники приёма вынесены в отдельные отношения. Пятая нормальная форма не требует декомпозиции, поскольку ни одно отношение не является соединением проекций с независимыми зависимостями. ## 2.7 Типы данных, домен и перечисления

Выбор типов данных подчинён трём правилам: тип должен запрещать недопустимые значения, не требовать преобразований при сравнении и сохранять однозначность при смене часового пояса. События хранятся в `timestamptz`, календарные даты (рождение, трудоустройство, срок договора) — в `date`, интервалы — в диапазонных типах `daterange` и `tstzrange`. Использование диапазонных типов позволяет применить ограничения `EXCLUDE` и индексы GiST, описанные в документации PostgreSQL [8, 9].

Для плановой вместимости палаты создан домен `positive_bed_count` с проверкой `VALUE > 0`: домен исключает ноль и отрицательные значения во всех местах использования и явно называет смысл типа. Для статуса госпитализации создан перечисляемый тип `hospitalization_status` со значениями `active`, `discharged`, `cancelled`: перечисление запрещает произвольные строки и уменьшает размер столбца. Остальные статусы и типы реализованы текстовыми столбцами с проверками `IN (...)`, поскольку их состав может расширяться и не требует отдельного типа.

Миграции 004 и 005 расширили справочники, не создавая новых таблиц: в `diagnoses` добавлены глава МКБ-10 (`chapter`) и признак активности (`is_active`), в `user_organization_scopes` — необязательная ссылка на отделение (`department_id`), а проверка кодов роли расширена до одиннадцати значений. Глава МКБ-10 является атрибутом кода диагноза и не создаёт транзитивной зависимости: она определяется самим кодом, а не пациентом или случаем. ## 2.8 Ограничения целостности

Ограничения целостности распределены по трём уровням: ограничения схемы (ключи, уникальности, проверки, исключения), межтабличные правила второй миграции и серверные проверки приложения. Такое распределение позволяет СУБД отклонять недопустимое состояние независимо от того, каким способом оно получено — через приложение, прямой SQL или импорт.

В схеме объявлено 69 внешних ключей, 70 проверок `CHECK` (включая проверку домена), 7 ограничений `EXCLUDE`, а также частичные уникальные индексы. Основные группы ограничений и их смысл приведены в таблице 9.

Отсутствие расширения привело бы к невозможности создать ограничения пересечения интервалов, поэтому проверка наличия расширений включена в порядок развёртывания.

## 2.9 Обоснование проектных решений

Выбор PostgreSQL обусловлен поддержкой диапазонных типов, ограничений `EXCLUDE` и индексов GiST, которые выражают правила интервалов декларативно; проверки только в коде не защищают от прямого SQL. Интервальная модель выбрана вместо хранения текущего состояния, поскольку состояние выводится из интервалов, а ограничения не позволяют создать два одновременных интервала.

Отказ от каскадного удаления обусловлен характером данных: удаление справочной записи не должно уничтожать историю лечения, а для ошибочных черновиков пациентов предусмотрена отдельная процедура с проверкой отсутствия связанных событий. Схема `project` выбрана по требованию к размещению объектов; служебные имена приложения (`medcore.actor_user_id`, `medcore.request_id`, `medcore_q01`–`medcore_q12`) сохраняют префикс `medcore`, поскольку являются именами приложения, а не схемы.

## 3.2 Таблицы, ключи и ограничения

Таблицы создаются в порядке, обеспечивающем существование родительских отношений к моменту объявления внешних ключей: сначала справочники организаций, затем структура, персонал, пациенты и события лечения, затем лабораторный контур, и в конце — контур доступа, аудита и отчётности. Такой порядок позволяет объявлять внешние ключи непосредственно в определении таблицы, не используя отложенные `ALTER TABLE`.

Каждая таблица имеет первичный ключ: для событийных отношений — суррогатный `bigint`, для связующих — составной естественный ключ. Внешние ключи обязательны, кроме случаев, где отсутствие связи имеет предметный смысл: поликлиника без головной больницы, учётная запись без карточки сотрудника, ссылка на предшественника при исправлении. Миграции 004 и 005 не создают новых таблиц, а расширяют существующие: в `diagnoses` добавлены глава МКБ-10 (`chapter`) и признак активности (`is_active`), в `user_organization_scopes` — необязательная ссылка на отделение (`department_id`) с индексом `idx_scopes_department`, а проверка `roles_code_check` допускает одиннадцать кодов роли. Ограничения проверки значений объявляются вместе со столбцом: для текстовых полей применяется проверка `btrim(поле) <> ''` (строка из пробелов не считается заполненной), для перечислимых — `IN (...)`, для согласованных состояний — составные проверки.

Ограничения пересечения интервалов объявлены семью конструкциями `EXCLUDE USING gist`. Они защищают от двух одновременных прикреплений пациента к поликлинике, двух пересекающихся трудоустройств в одной организации, двух стационаров одного пациента, двух размещений на одной койке, двух коек у одной госпитализации, двух лечащих врачей у одной госпитализации и двух консультативных назначений в одной организации. Семантика полуоткрытого интервала описана в подразделе 2.4; техническая основа ограничений соответствует документации PostgreSQL [8, 9].

Служебная таблица `business_rule_checks` не относится к предметной области. Она хранит идентификаторы транзакций, для которых запланирована отложенная проверка межтабличных правил, и в нормальном завершённом состоянии пуста.

## 3.8 Домен и перечисляемый тип

Домен `positive_bed_count` определён как `integer` с проверкой `VALUE > 0` и применён к столбцу `wards.planned_capacity`. Домен выбран вместо повторения проверки в каждом месте использования: он называет предметное понятие и обеспечивает одинаковое поведение при изменении правила.

Перечисляемый тип `hospitalization_status` содержит значения `active`, `discharged` и `cancelled`. Значение `cancelled` обозначает отменённую госпитализацию: такое событие не занимает койку, поэтому интервалы размещения создаются только при фактическом поступлении. Перечисление запрещает запись произвольного статуса: попытка вставить неизвестное значение завершается ошибкой `22P02`, что подтверждено проверкой `unknown hospitalization status rejected`.

Остальные статусы — случай лечения, приём, направление, заказ исследования, результат операции — реализованы текстовыми столбцами с проверками `IN (...)`. Это решение позволяет расширять состав значений новой миграцией без изменения типа и не требует приведения типов в запросах.

## 3.9 Реализация межтабличных бизнес-правил

Правила, которые невозможно выразить ограничениями одной строки, реализованы отложенными проверками. Перед изменяющим оператором триггер проверяет уровень изоляции `READ COMMITTED` и получает транзакционную advisory-блокировку; после оператора в служебную таблицу добавляется идентификатор транзакции, а перед `COMMIT` проверяется итоговое состояние. Разделение блокировки `BEFORE STATEMENT` и постановки проверки `AFTER STATEMENT` необходимо для режима `SET CONSTRAINTS ALL IMMEDIATE`, когда проверяется уже изменённое состояние. Многошаговые операции госпитализации, перевода и выписки выполняются в такой транзакции: промежуточное состояние может быть неполным, итоговое — нет.

Покрытые группы правил: научная квалификация, совместительство, консультации, допустимость дат, завершённость структуры, вместимость палаты, основание госпитализации, место лечения, непрерывность интервалов, лечащий врач, лабораторный заказ, результаты, состав участников операции и исправления записей.

Проверка намеренно глобальная: блокировка общая для всех участвующих записей, что упрощает доказательство последовательности, но ограничивает скорость записи. Для промышленной нагрузки потребуются локальные блокировки; транзакцию нельзя держать открытой во время ввода данных или сетевого запроса.

Функции постановки и исполнения проверок работают с правами владельца и фиксированным путём поиска объектов; у `PUBLIC` отозваны права на служебную очередь и прямой вызов функций. Рабочая роль приложения должна получить только необходимые права отдельной миграцией: владение схемой, управление триггерами и доступ к очереди ей не предоставляются.

# 4 ПРОЕКТИРОВАНИЕ И СОЗДАНИЕ ПРИЛОЖЕНИЯ

## 4.1 Архитектура приложения

Приложение построено по трёхуровневой архитектуре: клиент в браузере, сервер приложения и база данных. Браузер не имеет прямого доступа к СУБД: все операции выполняются через программный интерфейс сервера, который проверяет сессию, права и входные данные. Такая схема исключает передачу параметров подключения в клиент и позволяет применять ограничения доступа независимо от интерфейса.

Верхний уровень — одностраничное приложение на React с маршрутизацией в браузере. Средний уровень — сервер ASP.NET Core, который принимает HTTP-запросы, аутентифицирует сессию по cookie, формирует объект доступа пользователя и выполняет операции в транзакциях. Нижний уровень — PostgreSQL со схемой `project`, ограничениями целостности, представлениями, процедурами и функциями.

Локальный запуск предполагает два процесса: сервер API на порту 5180 и клиентское приложение Vite на порту 5173. Сервер разрешает кросс-доменные запросы только с двух локальных адресов клиента и требует совпадения `Origin` для небезопасных методов, что защищает от подделки межсайтовых запросов. Параметры подключения к базе данных задаются переменными окружения или локальным файлом, исключённым из контроля версий.

## 4.2 Технологический стек и его обоснование

Стек выбран по критериям поддержки, совместимости с PostgreSQL и возможности показать проектные решения на уровне СУБД. Состав стека и обоснование приведены ниже.

Серверная платформа — .NET 10 с ASP.NET Core: срок поддержки этой ветки охватывает дату сдачи проекта [10], а ASP.NET Core предоставляет конвейер обработки запросов, встроенные механизмы аутентификации и авторизации и минимальные API, использованные в проекте [11]. Целевая платформа зафиксирована в `Directory.Build.props` как `net10.0`; предупреждения компилятора трактуются как ошибки.

Доступ к данным реализован через EF Core и провайдер Npgsql: EF Core применяется для чтения и записи сущностей, а вызовы процедур, запросы с массивами и отчёты выполняются параметризованным SQL. Схема остаётся собственностью SQL-миграций: миграции EF Core не создаются и не применяются.

Клиентская часть — React 19 с TypeScript. React выбран как библиотека компонентного интерфейса с декларативным описанием состояния [12]; TypeScript обеспечивает статическую проверку типов данных, получаемых от API. Дополнительно используются React Router для маршрутизации, TanStack Query для кеширования и повторных запросов, React Hook Form и Zod для форм и проверки ввода, Recharts для диаграмм, Lucide для пиктограмм.

Формирование PDF выполняет PDFsharp; при отсутствии шрифта с кириллицей экспорт возвращает ошибку 503, а не PDF с некорректными символами.

## 4.3 Структура проекта

Проект разделён на серверную, клиентскую и инфраструктурную части. Разделение позволяет собирать и проверять части независимо и не смешивать предметную логику с доступом к данным.

Серверная часть включает четыре проекта. `Medcore.Domain` содержит доменные правила размещения пациента и не зависит от инфраструктуры. `Medcore.Application` содержит контракты запросов и ответов, модель доступа пользователя и политики `AccessPolicies`. `Medcore.Infrastructure` содержит контекст EF Core и хранилища: пациентов, организаций, сотрудников, госпитализаций, лабораторий, административные и отчётные. `Medcore.Api` содержит точку входа, обработчик сессионной аутентификации и группы маршрутов. Отдельный проект `Medcore.Tests` содержит модульные тесты.

Клиентская часть организована по страницам и общим компонентам. Файл `api.ts` выполняет запросы с передачей cookie и преобразованием ошибок Problem Details, `auth.tsx` хранит состояние пользователя и защищает маршруты, `types.ts` описывает контракты ответов. Общие компоненты панели, таблицы, состояний загрузки и ошибок вынесены в `components`; страницы разделов — в `pages`.

Инфраструктурная часть включает миграции, запросы, наполнение и проверки в каталоге `database`, а также служебные сценарии в каталоге `tools`: развёртывание на учебном сервере, наполнение демонстрационными данными, проверка API, проверка конкуренции и резервное копирование. Диаграмма классов приложения приведена в приложении А (рисунок А.13).

## 4.4 Серверная часть

Аутентификация построена на управляемых сессиях. При входе сервер проверяет логин и пароль, создаёт случайный секрет сессии из 32 байт, сохраняет в базе данных только его SHA-256 хеш и устанавливает cookie с этим секретом. Cookie имеет атрибуты `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS и срок жизни 8 часов. При каждом запросе обработчик ищет сессию по хешу, проверяет срок, отсутствие отзыва и активность учётной записи и формирует объект доступа с ролями и областями действия.

Пароли хранятся в виде хешей ASP.NET Identity V3 (PBKDF2-HMAC-SHA512, 210 000 итераций, случайная соль 16 байт, подключ 32 байта). Для несуществующего логина выполняется проверка по фиктивному хешу, что выравнивает время ответа и затрудняет перебор логинов. Частота попыток входа ограничена 20 запросами в минуту с одного адреса; при превышении возвращается код 429 с указанием времени повтора.

Авторизация выполняется в два шага: проверяется роль, затем контекст — учреждение регистратора, лаборатория сотрудника, отношение врача к пациенту. Отношение врача подтверждено, если он участвовал в событиях случая (приём, диагноз, запись, назначение, направление, заказ, операция, назначение лечащим врачом). Технический администратор медицинских карт не получает.

Списки формируются на сервере с постраничным выводом. Размер страницы ограничен значением 100, значения `page` и `pageSize` нормализуются. Поиск выполняется по фрагменту ФИО через `ILIKE` с параметром, а не конкатенацией строки запроса. Область доступа передаётся в выборку массивами идентификаторов, сформированными из сессии.

Операции с несколькими связанными записями выполняются в транзакциях `READ COMMITTED` с блокировкой строк через `SELECT ... FOR UPDATE`: поступление создаёт случай, госпитализацию, размещение, врача и диагноз; перевод закрывает прежнее размещение и открывает новое в один момент; выписка закрывает размещение, назначение врача и случай согласованно.

Ошибки возвращаются в формате Problem Details: нарушение ограничений базы данных преобразуется в код 409 без раскрытия текста SQL-ошибки, отсутствие записи — в код 404, недоступность базы данных — в код 503; к ответу добавляется идентификатор трассировки, не содержащий персональных данных.

Состояния загрузки, ошибки и отсутствия данных реализованы отдельными компонентами и используются на всех списках. Формы валидируют обязательные поля до отправки, а серверные ошибки отображаются рядом с формой. Интерфейс поддерживает работу с клавиатуры: элементы форм имеют подписи, кнопки — доступные имена, диалоги закрываются клавишей Escape. Визуальная концепция — тёмная палитра со стеклянными панелями; для таблиц и форм применяется плотный непрозрачный фон, чтобы медицинские данные оставались читаемыми.

## 4.6 Результаты тестирования

## 4.7 Производительность и оптимизация

Время отклика измерено отдельным прогоном `docs/database/checks/perf-report.json`: по десять замеров на эндпоинт, одна и та же сеть и один и тот же учебный PostgreSQL до и после правок. Значения p50 до и после: аутентификация — 491,7 → 2,8 мс, обзор — 1309,8 → 150,3 мс, список пациентов — 1120,1 → 116,9 мс, реестр организаций — 915,7 → 89,0 мс, отчёт о занятости — 964,1 → 100,6 мс, поиск по МКБ-10 — 591,9 → 91,2 мс; карточка пациента в дополнительном прогоне — 669,1 → 144,1 мс. Вход с проверкой пароля занимает 888,1 мс для врача и 645,6 мс для администратора организации, поскольку включает PBKDF2 с 210 000 итераций. Цели по времени отклика (обзор менее 700 мс, списки менее 600 мс) достигнуты по p50; p95 на учебном канале достигает 800 мс из-за неравномерной задержки сети, а не работы SQL.

Ускорение объясняется изменением числа обращений к базе и объёма передачи. Аутентификация вместо пяти последовательных запросов (пользователь, сотрудник, роли, области) выполняет один SQL с `json_agg`, а объект доступа кешируется в `IMemoryCache` по SHA-256 хешу токена (sliding 45 с, absolute 60 с) и удаляется при выходе. Обзор, счётчик со страницей списка, обзор отчётов, восемь справочников и карточка пациента с историей и аудитом выполняются одним пакетом `NpgsqlBatch`; проекции списка и карточки переписаны на `LATERAL`. Включено сжатие `brotli` и `gzip`: тело обзора уменьшается с 1927 до 611 байт (gzip) и 553 байт (brotli). На клиенте заданы `staleTime` 60 с, `gcTime` 600 с и отключено обновление при фокусе окна.

Дополнительные индексы не добавлялись, миграция 006 не создавалась: `EXPLAIN ANALYZE` показывает, что подсчёт пациентов занимает 2,2 мс, страница — 4,2 мс, а последовательное сканирование 1000 пациентов и 2000 случаев оптимально при таких объёмах. Наблюдаемые до оптимизации 500–1100 мс объясняются сетевым круговым обходом. Эквивалентность ответов проверена побайтным сравнением JSON старого и нового экземпляров; сборка сервера прошла без предупреждений, проверка типов клиента — без ошибок.

## 5.2 Аутентификация

Аутентификация выполняется по логину и паролю с созданием серверной сессии. В таблице `users` хранится хеш ASP.NET Identity V3: PBKDF2-HMAC-SHA512, 210 000 итераций, соль 16 байт, подключ 32 байта. Параметры зафиксированы в коде явно, чтобы обновление платформы не изменило их незаметно.

Секрет сессии формируется криптографическим генератором (32 байта); в базе хранится только его SHA-256 хеш, поэтому компрометация `user_sessions` не даёт воспользоваться сессией. Формат секрета проверяется до обращения к базе.

Сессия прекращается истечением срока (8 часов), явным выходом с установкой `revoked_at` или блокировкой учётной записи; при изменении ролей активные сессии отзываются, чтобы новое право не ожидало истечения cookie. Проверка `expires_at > CURRENT_TIMESTAMP` выполняется в запросе, поэтому истёкшая сессия не принимается даже при расхождении часовых поясов процесса.

Ограничение частоты попыток входа реализовано на уровне конвейера запросов: не более 20 попыток в минуту с одного IP-адреса, при превышении возвращается код 429 и заголовок `Retry-After`. Ограничение применяется только к маршруту входа и не влияет на рабочие запросы.

## 5.3 Авторизация

Авторизация основана на ролях с областью действия. Роль хранится в таблице `user_roles`, область действия — в `user_organization_scopes`, где указывается учреждение, лаборатория или отделение, но не более одного значения одновременно (проверка `num_nonnulls(...) = 1`; ссылка на отделение добавлена миграцией 004). Всего поддерживается одиннадцать ролей и четыре вида областей: учреждение, отделение, город и регион. Такое разделение позволяет одному пользователю иметь разные роли в разных учреждениях, не создавая дублирующих учётных записей.

Политики доступа реализованы как функции приложения и как условия в запросах. Функции `AccessPolicies` проверяют роль и наличие обязательного контекста: регистратор может зарегистрировать пациента только в своей поликлинике, врач — редактировать диагноз только при подтверждённом отношении к пациенту, администратор организации — изменять только своё учреждение. Для больничных ролей введена отдельная политика чтения: главный врач, заместитель и заведующий отделением получают пациентов больницы, но не всего города; структуру изменяет только главный врач, персоналом управляют главный врач и заместитель, а заведующий видит сотрудников и статистику своего отделения. Министр здравоохранения и губернатор не входят в политику чтения пациентов и получают данные только через агрегирующие отчёты: в запросах отчётов для них подставляется признак чтения всех организаций и отключаются персональные поля.

Области действия передаются в запросы массивами идентификаторов, сформированными из сессии. Браузер не может расширить область, передав свой массив: параметры области не принимаются из запроса. Фильтр по учреждению не заменяет проверку отношения врача к пациенту, поэтому для врача применяются оба условия.

Матрица прав проверена на уровне API: подтверждено, что администратор, менеджер организации, аналитик и сотрудник лаборатории не получают персональный список пациентов; врач получает пациентов в рамках отношений лечения и не получает право регистратора на изменение контактов; регистратор не может создать диагноз. Для новых ролей проверено, что главный врач, заместитель и заведующий видят 347 пациентов своей больницы, а министр и губернатор получают отказ 403 на карточки пациентов и работают только со сводными показателями. Отрицательные проверки для всех вложенных маршрутов и для изменения роли во время активной сессии выполнены не полностью.

## 5.4 Защита от SQL-инъекций и валидация данных

Все значения передаются в SQL как параметры. Конкатенация пользовательских значений в текст запроса отсутствует; динамически формируются только имена объектов в служебных функциях установки триггеров, где используются фиксированные списки таблиц и функция `format('%I')`. Запросы отчётов и списков имеют постоянную структуру, а необязательные условия реализованы через параметры и `COALESCE`-подобные конструкции. Параметризация как основная мера защиты от инъекций соответствует рекомендациям OWASP [13].

Валидация выполняется на трёх уровнях: клиент проверяет обязательные поля и форматы, сервер независимо повторяет проверку и возвращает ошибки с указанием полей, база данных контролирует ограничения схемы. Дублирование намеренно: клиентская проверка улучшает взаимодействие, серверная защищает интерфейс, ограничения СУБД защищают данные при любом способе записи.

Поиск по ФИО использует `ILIKE` с параметром. Символы `%` и `_` во входной строке остаются шаблонными символами, что позволяет искать по частичному совпадению, но означает, что пользователь может расширить шаблон. Это ограничение зафиксировано в описании запроса Q01; режим буквального поиска не реализован. Риск ограничен рамками области доступа: расширение шаблона не позволяет выйти за пределы разрешённых учреждений.

## 5.5 Аудит

Журнал аудита (`audit_logs`) фиксирует автора, время, действие, тип и идентификатор объекта, перечень изменённых полей, идентификатор запроса и исход. Значения персональных данных в журнал не копируются: для изменений пациента перечисляются имена столбцов, но не их содержимое.

Аудит изменений пациента реализован триггером `trg_audit_patient_changes` (после вставки, обновления и удаления). Автор задаётся транзакционным параметром `medcore.actor_user_id`, идентификатор запроса — `medcore.request_id`; параметры действуют на время транзакции и не переносятся на следующий запрос из пула. При отсутствии автора сохраняется NULL, что отличает техническую загрузку от пользовательской операции.

Кроме триггера, аудит выполняет приложение: фиксируются вход и выход, изменение учётной записи и ролей, чтение карточки пациента, поступление, перевод, смена врача, выписка, создание направления, заказа и результата. Административный экран фильтрует журнал по периоду и действию.

Аудит отказов реализован частично: неуспешный вход фиксируется, но отказы политик на рабочих маршрутах отдельными событиями не записываются. Ограничение отмечено в подразделе 5.7.

## 5.6 Резервное копирование и восстановление

Резервное копирование реализовано сценарием `tools/backup-db.mjs`: дамп схемы `project` в формате `pg_dump`, SHA-256 файла и манифест с временем, размером, версиями сервера и `pg_dump`, составом объектов и количеством строк ключевых таблиц. Схема `space_archive` копируется только по явному флагу.

Резервная копия создана 30 октября 2026 года: файл `medcore_project_only_20261030T155650Z.dump` размером 381 634 байта, контрольная сумма `9d09149d…`, формат custom, схема `project`, сервер PostgreSQL 18.0, `pg_dump` версии 18.6. В манифесте зафиксированы 48 таблиц, 3 представления, 4 процедуры и 11 функций, а также количество строк ключевых таблиц: 1000 пациентов, 2000 случаев, 500 госпитализаций, 500 размещений, 300 коек, 200 сотрудников, 120 врачей, 1500 приёмов. Создание копии заняло 57 079 мс; `pg_dump` выдал 30 предупреждений, текст которых в манифест не включён.

Восстановление выполняет сценарий `tools/restore-db.mjs`. Он отказывается работать, если имя целевой базы совпадает с рабочей базой из `.env` или со служебной базой, если в целевой базе уже есть схемы `project` или `space_archive` и если SHA-256 файла не совпадает с манифестом. Перед записью архив читается через `pg_restore --list`: 534 записи, в том числе 48 блоков `TABLE DATA`. Восстановление выполняется с параметрами `--no-owner --no-privileges --single-transaction --exit-on-error`, поэтому при ошибке не остаётся частично восстановленной схемы.

Восстановление проверено в отдельном временном кластере PostgreSQL 18.6. База `medcore_restore_check` создана сценарием, `pg_restore` завершился с кодом 0 за 1339 мс; совпали 10 из 10 ключевых таблиц, найдены 3 из 3 представлений и 4 из 4 процедур, восстановлены 48 таблиц, 11 функций и расширения `btree_gist`, `pg_trgm`. На учебном сервере восстановление в отдельную базу заблокировано средой: роль не имеет права `CREATE DATABASE` (SQLSTATE 42501), поэтому проверка выполнена на локальном кластере, а не на самом сервере. Машинные поля приведены в `docs/database/checks/backup-restore.json`, порядок действий — в `docs/user-manual/backup-restore.md`.

Ограничения: копия логическая, расписания, внешнего хранения, шифрования копий и WAL/PITR нет; восстановление на учебном сервере потребует администратора СУБД.

## 5.7 Ограничения среды и остаточные риски

Ограничения среды подтверждены проверками и настройками. Учебный сервер PostgreSQL не поддерживает SSL: попытка защищённого соединения завершилась неудачей, в локальных настройках выбран обычный режим. Канал между приложением и базой данных в текущей конфигурации не шифруется. Учебная роль не является суперпользователем и не может создавать роли базы данных, поэтому отдельная роль приложения с минимальными привилегиями не создана; приложение работает от имени владельца схемы. Следствие: владелец может отключать триггеры и обходить ограничения, а проверка IT-19 «обычная роль не может отключить защитный триггер» не выполнена.

Остаточные риски, существенные для защиты, перечислены ниже.

1. Отсутствие TLS на учебном сервере означает, что содержимое сессионных cookie и данные запросов могут быть перехвачены в сети. Для промышленной эксплуатации требуется HTTPS и режим SSL для подключения к СУБД.

2. Приложение подключается к базе данных с правами владельца схемы. Разделение прав на роль чтения, роль записи и роль обслуживания не выполнено.

3. Аудит отказов в доступе не реализован, поэтому попытки обращения к чужим картам не образуют отдельного потока событий.

4. Управление сроком доступности выгрузок не реализовано: таблица `report_exports` создана, но приложение формирует файл в ответе на запрос и не сохраняет его с ограниченным сроком. Повторная проверка прав при скачивании по идентификатору отсутствует, поскольку постоянные файлы не создаются.

5. Эффективность индексов не измерена на демонстрационном наборе: протоколы `EXPLAIN ANALYZE` отсутствуют.

6. Двадцать четыре интеграционных сценария IT-01–IT-24 и полный набор отрицательных проверок прав не выполнены; подтверждены отдельные сценарии и ограничения.

7. Полное соответствие специальности лечащего врача специализации отделения не проверяется: между справочниками нет явной таблицы соответствия, а сравнение текстовых кодов не применяется.

8. Проверка действующего трудоустройства открытого назначения выполняется на момент изменения данных, а не при наступлении календарной даты увольнения.

9. Роли министра здравоохранения и губернатора различаются только подписью рабочей области: права одинаковые, поэтому разграничение города и региона не является техническим ограничением доступа.

10. Область отделения заведующего проверяется приложением и не ограничена отдельной проверкой схемы: `department_id` допускается для любой роли, а допустимость обеспечивает код.

## 5.8 Выводы по разделу

Реализованы аутентификация с хешированием паролей и управляемыми сессиями, авторизация по ролям с областями действия, параметризация запросов, трёхуровневая валидация, аудит и резервное копирование с контрольной суммой. Остаточные риски связаны с отсутствием TLS и разделения прав на учебном сервере, неполным аудитом отказов и невозможностью восстановления на учебном сервере без права `CREATE DATABASE`.

# ЗАКЛЮЧЕНИЕ

В ходе курсового проекта разработана информационная система MEDCORE для медицинских организаций города. Цель проекта достигнута в объёме, подтверждённом машинными протоколами проверок: спроектирована и создана реляционная база данных, реализовано трёхуровневое приложение с разграничением доступа, подготовлены демонстрационные данные и средства проверки.

Анализ предметной области выполнен: выделены шесть процессов, одиннадцать ролей с четырьмя видами областей действия, четырнадцать функциональных и десять нефункциональных требований, построена функциональная модель IDEF0. Спроектирована реляционная модель из 48 отношений, покрывающая организации и структуру, персонал, пациентов и случаи лечения, стационар, лабораторный контур и контур доступа. Модель нормализована до третьей нормальной формы; два технических дублирования обоснованы требованиями целостности. Определены типы данных, домен положительной вместимости, перечисление статуса госпитализации и 69 внешних ключей.

Созданы объекты базы данных: 48 таблиц, 57 индексов, 3 представления, 4 процедуры, 11 функций, 111 триггеров и 7 ограничений исключения интервалов. Миграции 004 и 005 расширили справочники: одиннадцать ролей, область отделения, 47 кодов МКБ-10 с главами и 14 врачебных специальностей; в карточке пациента появился блок «История болезни» с хронологией диагнозов, записей, госпитализаций и исследований. Реализован механизм отложенных межтабличных проверок с транзакционной блокировкой и защитой исторических связей. Двенадцать обязательных запросов подготовлены как параметризованные выражения и выполнены на демонстрационном наборе; результат иерархического запроса Q10 (447 узлов) совпал с суммой объектов структуры, что подтверждает корректность рекурсивного обхода.

Реализовано приложение: сервер ASP.NET Core с сессионной аутентификацией, политиками доступа, транзакционными операциями поступления, перевода и выписки, отчётами и экспортом в CSV и PDF; клиент React с восемью разделами, серверным поиском и отчётами. Серия протоколов подтвердила 189 утверждений в пяти наборах проверок: регистрацию и поиск пациента, изменение контактов с контролем версии, запрет редактирования диагноза регистратору, отсутствие доступа к персональным картам у администратора, аналитика, министра и губернатора, матрицу доступа одиннадцати ролей, а также время отклика основных экранов (p50 обзора 150 мс, списка пациентов 117 мс). Реализованы меры защиты: хеширование паролей, управляемые сессии с хранением хеша секрета, ограничение частоты входов, параметризация запросов, трёхуровневая валидация, аудит изменений и резервное копирование с контрольной суммой.

Часть проверок осталась за пределами выполненного объёма, что ограничивает выводы. Взаимодействие с браузером, двадцать четыре интеграционных сценария приёмки и проверка прав ограниченной роли базы данных не выполнены; проверки новых ролей подтверждены протоколом `api-roles-report.json` (42 из 42). Восстановление резервной копии проверено в отдельном локальном кластере PostgreSQL 18.6, но не на учебном сервере: роль не имеет права `CREATE DATABASE` (SQLSTATE 42501). Отчёт Q02 о стаже первоначально не возвращал строк из-за одинаковых дат приёма в демонстрационном наборе; после исправления набора запрос возвращает 20 врачей выше среднего. Учебный сервер не поддерживает SSL, а отдельная роль приложения не создана.

Направления дальнейшей работы определены ограничениями: создание роли приложения с минимальными привилегиями и проверка невозможности обхода защитных триггеров; получение права `CREATE DATABASE` для проверки восстановления на учебном сервере, введение расписания копирования и шифрования копий; выполнение полного набора приёмочных сценариев и проверка интерфейса в браузере; контроль p95 на стабильном канале и проверка индексов на промышленном объёме данных.

**Листинг Б.3 — интервальные ограничения размещения на койке:**

CREATE TABLE bed_occupancies (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    hospitalization_id bigint NOT NULL REFERENCES hospitalizations(id),
    bed_id bigint NOT NULL REFERENCES beds(id),
    started_at timestamptz NOT NULL,
    ended_at timestamptz,
    CHECK (ended_at IS NULL OR ended_at > started_at),
    EXCLUDE USING gist (bed_id WITH =, tstzrange(started_at, ended_at, '[)') WITH &&),

**Листинг Б.4 — запрос Q10, рекурсивный обход структуры учреждения:**

```sql
WITH RECURSIVE nodes AS (
    SELECT 'hospital:' || o.id AS node_id, NULL::text AS parent_id,
        o.name AS label, 'hospital'::text AS node_type
    FROM project.hospitals h JOIN project.medical_organizations o ON o.id = h.organization_id
    WHERE o.id = ANY($1)
    UNION ALL
    SELECT 'building:' || id, 'hospital:' || hospital_id, code, 'building' FROM project.buildings
    UNION ALL
    SELECT 'department:' || id, 'building:' || building_id, name, 'department' FROM project.departments
    UNION ALL
    SELECT 'ward:' || id, 'department:' || department_id, number, 'ward' FROM project.wards
    UNION ALL
    SELECT 'bed:' || id, 'ward:' || ward_id, number, 'bed' FROM project.beds
), tree AS (
    SELECT node_id, parent_id, label, node_type, 0 AS depth, ARRAY[node_id] AS path
    FROM nodes WHERE parent_id IS NULL
    UNION ALL
    SELECT n.node_id, n.parent_id, n.label, n.node_type, t.depth + 1, t.path || n.node_id
    FROM nodes n JOIN tree t ON n.parent_id = t.node_id
    WHERE NOT n.node_id = ANY(t.path)
)
SELECT node_id, parent_id, label, node_type, depth FROM tree ORDER BY path;
```
