# Хранимые объекты и запросы MEDCORE

Миграция `003_stored_objects.sql` подготовлена для выполнения после `001_initial_schema.sql` и `002_business_rules.sql`. Она содержит три представления, четыре процедуры пациента, две расчётные функции и две служебные триггерные функции. Это исходный код для интеграции, а не подтверждение работы API: приложение ещё не подключено к этим объектам.

## Представления и единица результата

| Представление | Одна строка | Поля и семантика |
|---|---|---|
| `vw_hospital_capacity` | Отделение | Больница, отделение, физические койки, занятые сейчас, свободные доступные, недоступные незанятые, процент физической занятости |
| `vw_doctor_statistics` | Врач | ФИО, действующие специальности, текущие работодатели, завершённые приёмы, операции с завершённым исходом, летальные исходы |
| `vw_patient_treatment_summary` | Пациент | Неотменённые случаи и госпитализации, последнее обращение, текущий статус лечения |

Вместимость считается по отдельным физическим койкам. Занятость определяется попаданием текущего момента в полуоткрытый интервал размещения. Доступность свободной койки дополнительно учитывает активность койки, палаты, отделения, корпуса и больницы. Поэтому выполняется равенство `total_beds = occupied_beds + free_beds + unavailable_beds`. В отделении без коек процент равен NULL, поскольку деление на ноль не имеет содержательного результата.

Статистика врачей строится из независимых агрегатов на уровне врача. Соединение операций с приёмами и специальностями до агрегации умножило бы строки; здесь такие наборы соединяются уже после подсчёта. Каждый завершённый приём засчитывается каждому его участнику один раз. Каждая завершённая операция засчитывается каждому врачу-участнику один раз, независимо от роли. Показатели разных врачей нельзя суммировать как количество уникальных операций учреждения; для этого нужен отдельный агрегат по операции.

Сводка пациента считает последнее обращение как максимум открытия неотменённого случая и завершённого приёма. Для активной госпитализации учитывается текущий момент. Открытый случай без текущей госпитализации обозначается `outpatient`; отсутствие открытых случаев — `not_in_treatment`. Это рабочая классификация экрана, а не медицинский диагноз.

Все три представления охватывают всю базу. Их нельзя напрямую отдавать пользователю без проверки контекста. Например, сводка пациента содержит события разных учреждений, поэтому запрос списка Q01 рассчитывает доступную сводку отдельно по уже разрешённым учреждениям. Общий итог и итог в пределах учреждения должны быть явно подписаны в интерфейсе.

## Расчётные функции

`fn_department_occupancy(department_id)` возвращает процент занятых физических коек отделения с округлением до двух знаков. Если отделение не найдено либо не имеет коек, результат NULL. Активность койки не удаляет её из физического коечного фонда; доступность отдельным показателем отражается в представлении.

`fn_doctor_experience(doctor_id, as_of_date DEFAULT CURRENT_DATE)` возвращает эквивалент стажа в годах с округлением до двух знаков. Сначала кадровые интервалы объединяются средствами `range_agg`, затем суммируется число календарных дней и делится на 365,2425. Это не юридический расчёт стажа и не возраст по календарным годовщинам; интерфейс должен показывать подпись «Стаж, лет (расчёт по дням)».

Начало кадрового интервала включается, `ended_on` исключается. День `as_of_date` включён в расчёт. Будущие назначения не учитываются. Перекрывающиеся работа в больнице и поликлинике не удваивают стаж; доля ставки не умножает длительность. Консультативные назначения в расчёт не входят. Для существующего врача без кадровых интервалов возвращается 0; для несуществующего врача — NULL. Функция использует кадровую историю сотрудника, поэтому источники этой истории должны быть проверены при заполнении.

`range_agg` и multirange требуют PostgreSQL 14 или новее. Окончательная поддерживаемая версия PostgreSQL будет закреплена в инфраструктуре проекта.

## Процедуры пациента

`sp_register_patient` принимает ФИО, дату рождения, пол, телефон, почту и адрес; выходной `INOUT p_patient_id` возвращает новый ключ. Проверяются обязательные данные, допустимый пол и отсутствие будущей даты рождения. Совпадение ФИО и даты рождения не объявляется уникальностью, так как разные люди могут иметь одинаковые данные. Прикрепление оформляется отдельной операцией в той же транзакции при необходимости.

`sp_update_patient` изменяет только телефон, почту и адрес. Она требует ожидаемую версию карточки и отклоняет обновление, если карточка уже изменена другим пользователем. NULL или пустая строка в контактном аргументе очищает поле; это полная замена набора контактных полей, а не PATCH. Идентифицирующие и медицинские сведения в этой процедуре не изменяются.

`sp_delete_patient_draft` блокирует строку пациента и проверяет ожидаемую версию. Физическое удаление разрешается только при отсутствии медицинских случаев, госпитализаций и истории прикреплений. Проверка намеренно строже формулировки «без медицинских событий»: даже прикреплённая карточка уже не считается чистым черновиком. Для неё применяется деактивация. Действующие внешние ключи дополнительно препятствуют удалению при конкурентной вставке связанной записи. Удаление не каскадное, журнал аудита сохраняется.

`sp_get_patient_summary` возвращает курсор. Вызов и чтение должны находиться в одной транзакции. Пример для владельца схемы в учебной БД:

```sql
BEGIN;
CALL project.sp_get_patient_summary(1, 'patient_summary');
FETCH ALL FROM patient_summary;
COMMIT;
```

До вызова процедуры API обязан проверить доступ к конкретному пациенту. Статус технического администратора не разрешает чтение автоматически. Пример выше показывает только контракт PostgreSQL и не является сценарием обхода проверки прав.

## Аудит и версии

Триггер `trg_patient_row_version` перед каждым UPDATE увеличивает `version` и обновляет `updated_at`. Триггер `trg_audit_patient_changes` после INSERT, UPDATE или DELETE записывает вид операции, ключ пациента, время, автора, перечень изменившихся полей и идентификатор запроса. Значения персональных данных в журнал не копируются. При обновлении в перечень попадут и служебные `version`/`updated_at`.

Автор задаётся доверенным сервером через транзакционный параметр `medcore.actor_user_id`; идентификатор запроса — через `medcore.request_id`. Значение автора, если передано, должно ссылаться на активную учётную запись. При отсутствии значения сохраняется NULL, что позволяет отличать техническую загрузку от пользовательской операции, но не заменяет отдельную идентификацию технической роли.

Пользователь БД, способный произвольно выполнять SQL и менять эти параметры, может подставить другого автора. Следовательно, параметры сами по себе не являются авторизацией. При интеграции потребуются закрытый доступ к БД, контролируемая роль API, минимальные привилегии и серверная установка параметров после аутентификации. Используется `set_config(..., ..., true)` либо `SET LOCAL` в транзакции, чтобы контекст не утёк следующему запросу из пула соединений.

Все функции и процедуры исполняются с правами вызывающего пользователя (`SECURITY INVOKER`). PUBLIC лишается автоматического исполнения функций и процедур данной миграции. Конкретные GRANT будут настроены вместе с ролями БД; текущая миграция не создаёт законченного контура прав. Неудачная транзакция откатывает и её аудит успешных изменений. Отказы в доступе, ошибки входа и прочие неуспешные попытки должны журналироваться сервером отдельно.

## Двенадцать обязательных запросов

Файл `database/queries/required_queries.sql` содержит 12 именованных `PREPARE`. Его можно применить в одной сессии после миграций: PostgreSQL проверит привязку имён и типов, но данные выбираются только при `EXECUTE`. В будущем API сможет использовать тело каждого запроса с типизированными параметрами Npgsql. Повторная загрузка файла в той же сессии требует предварительного освобождения соответствующих prepared statements.

| Запрос | Параметры | Планируемое применение |
|---|---|---|
| Q01 | Фрагмент ФИО; разрешённые учреждения; размер страницы; смещение | Поиск пациентов с доступной сводкой |
| Q02 | Дата расчёта; разрешённые учреждения | Отчёт о стаже выше среднего |
| Q03 | Разрешённые больницы | Сравнение текущей нагрузки отделений |
| Q04 | Дата; разрешённые учреждения | Учреждения с действующими лабораторными договорами |
| Q05 | Больница; поликлиника; дата | Сравнение состава врачей через INTERSECT/EXCEPT/UNION ALL |
| Q06 | Начало и конец периода; разрешённые больницы | Поступления, выписки и занятые койко-дни |
| Q07 | Порог занятости; разрешённые больницы | Отделения с высокой загрузкой через HAVING |
| Q08 | Госпитализация; разрешённые больницы | Карточка с отделением поступления и текущим размещением |
| Q09 | Начало и конец периода; разрешённые больницы | Возраст при поступлении и длительность лечения |
| Q10 | Разрешённые больницы | Иерархия больница → корпус → отделение → палата → койка |
| Q11 | Год; разрешённые больницы | Сводная таблица поступлений по 12 месяцам |
| Q12 | Начало и конец периода; разрешённые больницы | Рейтинг отделений по поступлениям с оконными функциями |

Периоды времени полуоткрытые: начало включается, конец исключается. Q06 считает койко-дни по фактическим интервалам размещения в отделениях, а поступления и выписки — по больнице госпитализации. Q12 оценивает нагрузку поступлений по отделению поступления, а не текущую занятость коек. Для текущего размещения используются Q08 и представление коечного фонда.

Месяцы отчёта Q11 и возраст Q09 определяются по `Europe/Moscow` независимо от часового пояса сессии. В Q06/Q09 длительность в днях означает фактические секунды, делённые на 86400, а не число пересечённых календарных дат. API должен проверять порядок границ и допустимый год (1–9998); пустой набор разрешённых учреждений возвращает пустой результат.

Каждый массив разрешённых учреждений формируется после проверки пользователя, а не принимается от браузера как доверенный. Для врача дополнительно нужна проверка отношений с пациентами; фильтр организации не заменяет это правило. Q05 также требует проверки обоих работодателей и их типов. Подстановки строк в SQL отсутствуют; `%` и `_` в Q01 остаются шаблонными символами ILIKE, пока продукт не определит режим буквального поиска.

## Проверки перед подключением API

В изолированном PGlite 0.3.14 на PostgreSQL 17.5 выполнены три миграции, подготовлены и исполнены все 12 запросов на пустых данных. Это подтверждает привязку имён и типов, но не правильность содержательных результатов каждого отчёта.

Файл `database/tests/003_stored_objects.sql` прошёл в том же окружении на временных вымышленных данных с последующим ROLLBACK. Он проверяет регистрацию, нормализацию контактов, изменение версии и отказ устаревшему обновлению; аудит автора и изменённых полей; удаление черновика и отказ для пациента с медицинским случаем; курсор сводки; объединение перекрывающихся трудовых интервалов и исключение будущей работы; нулевую, недоступную и доступную вместимость; подсчёт двух приёмов, двух операций и одного летального исхода при наличии нескольких специальностей без умножения строк.

Отдельный многопользовательский сервер PostgreSQL, права ролей, конкурентные сессии и производительность этими проверками не охвачены. Для отчётов Q01–Q12 ещё нужны сценарии с заполненными данными, периодами, переводами между отделениями и ограничениями доступа. Машинный результат общего прогона находится в `docs/database/checks/pglite-report.json`.
