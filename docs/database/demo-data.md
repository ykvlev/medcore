# Демонстрационные данные MEDCORE

`database/seeds/demo.sql` формирует воспроизводимый набор вымышленных данных в схеме `project`. Никакие данные реальных пациентов, учреждений и контактов не используются. Почтовые адреса находятся в домене `example.test`, телефоны имеют демонстрационный код `000`, а адреса явно относятся к «Учебному городу».

## Объём и связи

| Объект | Количество |
|---|---:|
| Больницы | 5 |
| Поликлиники | 8 |
| Корпуса | 12 |
| Отделения | 30 |
| Палаты | 100 |
| Койки | 300 |
| Врачи | 120 |
| Остальные сотрудники | 80 |
| Пациенты | 1000 |
| Медицинские случаи | 2000 |
| Госпитализации | 500 |
| Завершённые госпитализации | 400 |
| Активные госпитализации | 100 |
| Операции | 200 |
| Лаборатории | 6 |
| Лабораторные договоры | 20 |
| Лабораторные заказы | 600 |
| Результаты исследований | 500 |
| Демонстрационные пользователи | 6 |

Дополнительно создаются 1500 завершённых приёмов, 2000 основных диагнозов, 2000 записей осмотра и 2000 назначений. Названия диагнозов и назначения намеренно учебные и не содержат лечебных рекомендаций. Среди 200 операций предусмотрено пять вымышленных летальных исходов для проверки статистики.

Все палаты имеют три койки. Структура распределена по всем пяти больницам, и учреждения активируются после создания корпусов, отделений, палат и коек. Первые шесть поликлиник прикреплены к больницам, две работают самостоятельно. Все 1000 пациентов имеют текущее прикрепление к одной поликлинике.

Из 2000 случаев 1500 амбулаторные, 500 стационарные. Каждая госпитализация связана с ранее оформленным направлением того же пациента. В отделении поступления совпадает специализация направления. Истории койки и лечащего врача непрерывно покрывают срок госпитализации. Завершённые размещения разделены во времени; 100 активных размещений занимают разные койки. При загрузке получается 100 занятых и 200 свободных коек.

Врачи распределены по 24 на больницу и имеют по одному совместительству в поликлинике. Даты начала работы различаются, поэтому запрос стажа выше среднего возвращает содержательный результат. Перекрывающиеся назначения не удваивают стаж. Учёные звания соответствуют степеням; у пяти профессоров созданы консультативные назначения в нескольких поликлиниках. Сотрудники `manager` и `registrar` трудоустроены в больнице №1 и поликлинике №1, что соответствует выданным им областям доступа.

Все шесть лабораторий имеют три профиля. Для каждой организации создан договор, дополнительно предусмотрены семь договоров. Пятьсот готовых результатов и сто незавершённых заказов относятся к лаборатории №1: это позволяет единственной демонстрационной учётной записи лаборатории работать строго в своей области. Другие пять лабораторий имеют действующие договоры и готовы к созданию новых заказов, но им не приписываются результаты, внесённые чужим пользователем. Пятьсот результатов введены пользователем `lab`, которому назначена именно лаборатория №1.

## Опорная дата

По умолчанию используется дата `2026-10-30` по Москве. Все интервалы относительно неё определяются формулами без случайного генератора. Завершённые госпитализации относятся к предыдущим месяцам; активные начались за три дня до опорной даты. Договоры действуют от года до неё до года после неё. Переопределение даты доступно через `--anchor=YYYY-MM-DD`, допустим диапазон от 01.01.2020 до текущей московской даты.

Идентификаторы генерируются БД, а связи строятся через временные таблицы сопоставления. Поэтому набор сохраняет смысл при ранее использованных значениях последовательностей, например после тестовых транзакций с ROLLBACK. Контрольные количества проверяются SQL до фиксации транзакции.

Соль пароля, время создания пользователей и время технического аудита естественным образом различаются между загрузками. Детерминированность относится к предметным данным, распределению и историческим интервалам, а не к побайтовому совпадению резервной копии.

## Пользователи и области

| Логин | Роль | Область |
|---|---|---|
| `admin` | Системный администратор | Технические функции; медицинские области не назначены |
| `manager` | Администратор организации | Учебная больница №1 и поликлиника №1 |
| `doctor` | Врач | Врач №1, работающий в больнице №1 и поликлинике №1 |
| `registrar` | Регистратор | Больница №1 и поликлиника №1 |
| `lab` | Сотрудник лаборатории | Лаборатория №1 |
| `analyst` | Аналитик | Агрегированная отчётность по всем 13 организациям |

Все шесть учётных записей используют пароль из переменной окружения `MEDCORE_DEMO_PASSWORD`. Сам пароль отсутствует в SQL, отчётах и консольном выводе. Перед загрузкой на сервер он должен быть задан и содержать не менее 12 символов. Подменять его паролем подключения к PostgreSQL нельзя.

Скрипт формирует хеш в формате ASP.NET Identity V3: PBKDF2-HMAC-SHA512, 210000 итераций, случайная соль длиной 16 байт и ключ длиной 32 байта. Заголовок содержит маркер формата и параметры в big-endian. Все шесть сохранённых хешей проверяются после загрузки. При локальной проверке без переменной используется случайный одноразовый пароль, который не выводится и не сохраняется.

Загрузку выполняет техническая роль владельца схемы, а не демонстрационный системный администратор. Поэтому аудит создания 1000 пациентов отмечен идентификатором запроса `medcore-demo-seed` и не приписан пользователю с клиническими полномочиями. Сохранённые области пользователей являются входными данными для политик API, а не самостоятельной защитой HTTP-маршрутов.

## Запуск и защита существующих данных

По умолчанию скрипт `tools/seed-educational-db.mjs` работает только с отдельной базой PGlite в памяти:

```powershell
node tools/seed-educational-db.mjs --local-check
```

Он создаёт пустую локальную базу, выполняет текущие миграции, загружает весь набор в одной транзакции и проверяет результат. Подключение к учебному серверу в этом режиме не выполняется. Локальный отчёт сохраняется в `docs/database/checks/local-seed-report.json`.

Отдельный режим для уже подготовленной учебной БД:

```powershell
node tools/seed-educational-db.mjs --server
```

Этот режим читает параметры подключения и демонстрационный пароль из окружения либо локального `.env`, проверяет ожидаемые имя базы, пользователя и владельца схемы `project`. Он не создаёт схему, не применяет миграции к серверу и не затрагивает другие схемы. Применять его следует после проверки локального отчёта и готовности серверной схемы.

Если в MEDCORE уже есть пациенты, медицинские случаи, организации, сотрудники, лаборатории или пользователи, загрузка отклоняется с SQLSTATE `55000`. Она ничего не удаляет и не пытается автоматически очищать базу. Повторное применение также отклоняется. Предметные триггеры и ограничения не отключаются. При ошибке до COMMIT откатывается весь набор; значения последовательностей при этом могут продвинуться, что является обычным свойством PostgreSQL.

Парольный хеш передаётся параметризованным `set_config` внутри транзакции через `medcore.seed_password_hash`, дата — через `medcore.seed_anchor_date`. Внешние BEGIN/COMMIT из SQL снимаются только runner-ом, чтобы настройка параметров и наполнение находились в одной общей транзакции.

## Фактическая локальная проверка

Полное наполнение проверено в PGlite 0.3.14 на PostgreSQL 17.5. Успешно завершились миграции, загрузка всех объёмов, отложенная проверка бизнес-правил при COMMIT и контроль вместимости 300/100/200. Проверены форматы хешей шести пользователей, наличие правильной лабораторной области у авторов результатов, попадание дат направлений в сроки исходных случаев и соответствие областей врача, регистратора и администратора их трудоустройству. Подготовлены и выполнены все 12 запросов на заполненном наборе. Повторная загрузка получила ожидаемый отказ `55000`.

Эта проверка не подтверждает производительность многопользовательского сервера, конкурентные сессии, права роли API и отображение результатов в интерфейсе. На момент подготовки набора серверная загрузка этим агентом не выполнялась. Для неё создаётся отдельный `educational-seed-report.json` после явного запуска серверного режима.

## Точечная корректировка первой серверной загрузки

При дополнительной проверке первой версии набора обнаружены два несоответствия: 500 направлений были оформлены после слишком рано заданной даты закрытия исходного амбулаторного случая; трудоустройство `manager` и `registrar` не совпадало с их областями доступа. В текущем SQL эти данные формируются согласованно с самого начала: исходные случаи закрываются через час после оформления направления, а оба сотрудника работают в больнице №1 и поликлинике №1.

Для уже загруженной первой версии подготовлен `tools/fix-demo-consistency.mjs`. По умолчанию он выполняет только `BEGIN READ ONLY` и показывает план. Режим `--apply` изменяет исключительно отмеченные демонстрационные случаи и трудовые назначения после проверки имени БД, пользователя, владельца схемы, контрольных количеств, названий учреждений, логинов и синтетических почтовых адресов сотрудников. Существующие пациенты, врачи, медицинские события и пользователи не удаляются.

Проверенный план первой версии: 500 дат закрытия случаев, два переноса основного учреждения сотрудников и два добавления совместительства в поликлинике. Перед COMMIT повторно проверяются все бизнес-правила и согласованность направлений и областей. Повторное применение после успешной коррекции не вносит изменений. Отчёт находится в `docs/database/checks/demo-consistency-correction.json`; статус `review_ready` означает только проверенный план, `passed` — успешное применение.
