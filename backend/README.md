# Сервер MEDCORE

ASP.NET Core 10, PostgreSQL, EF Core для обычных моделей чтения и Npgsql для процедур, сессий и аналитических запросов. Источник схемы — SQL-миграции проекта; EF не создаёт и не изменяет таблицы автоматически.

Пять проектов: Api, Application, Domain, Infrastructure и Tests. Конфигурация подключения поступает из `ConnectionStrings__Medcore` либо стандартных переменных `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE`. Сервер сам не читает `.env`: окружение передаёт общий локальный запускатель. Пароль не сохраняется в исходниках.

По умолчанию API слушает localhost:5180; клиент использует прокси с localhost:5173. `/health` проверяет наличие работающего HTTP-процесса, не подтверждая доступность БД. Описание API находится в `/openapi/v1.json`, Swagger UI — в `/swagger`.

## Реализуемый вертикальный срез

Вход, выход, проверка сессии; обзор с реальными показателями; поиск пациентов с пагинацией; доступная пользователю карточка и история; регистрация с прикреплением в разрешённой поликлинике; изменение только контактов с проверкой версии. Дополнительно доступны чтение организаций, персонала, госпитализаций, лабораторий и обзор аналитических отчётов. Диагноз добавляет врач в доступный ему медицинский случай.

Сессия — непрозрачный случайный токен 256 бит в HttpOnly cookie; в БД хранится только SHA-256 токена, срок и отзыв. Пароли проверяет IdentityV3 PasswordHasher с PBKDF2. Cookies имеют SameSite=Lax; небезопасные браузерные методы дополнительно проверяют Origin. Вход ограничен двадцатью попытками в минуту на IP. Эти настройки рассчитаны на локальную учебную демонстрацию; HTTPS и доверенный reverse proxy настраиваются отдельно при сетевом размещении.

Технический администратор не получает медицинские карты автоматически. Регистратор видит пациентов по текущему прикреплению или открытому случаю в своей области. Врач дополнительно должен иметь подтверждённое участие в медицинском случае доступной организации. История врача ограничена такими случаями. Регистратор не получает диагнозы и тексты медицинских записей в истории. Организационный администратор видит обезличенный список размещений и агрегаты.

Удаление пациента через API пока не реализовано: процедура черновиков существует, но отдельный устойчивый контекст владения черновиком не определён. Полные CRUD остальных разделов, выгрузки CSV/PDF, управление ролями и транзакции госпитализации через интерфейс остаются следующими этапами.

## Проверка

```powershell
.\.tools\dotnet\dotnet.exe build backend/Medcore.slnx
.\.tools\dotnet\dotnet.exe test backend/Medcore.Tests/Medcore.Tests.csproj
```

Модульные проверки не заменяют интеграционные: API нужно отдельно проверить с реальной БД и каждой демонстрационной ролью. Доступ SQL-пользователя к схеме и процедурам должен быть выдан явно; текущая учебная учётная запись владельца не доказывает корректность минимальных привилегий будущей рабочей роли.
